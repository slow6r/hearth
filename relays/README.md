# relays/ — конфигурация релеев

**Кода upstream здесь нет, и правок к нему — ровно одна.** Ini-файлы, init-скрипты,
процедура проверки бинарей и один патч к push-серверу (`ntf/patches/`, ADR 0016): без
него ntf-server upstream шлёт пуши только приложению SimpleX. Любой другой diff к
Haskell-коду SimpleX — блокер ревью (ТЗ §2.2, §8.3).

```
relays/
├── smp/        smp-server.ini.example + init-smp.sh
├── xftp/       file-server.ini.example + init-xftp.sh
├── ntf/        push-сервер для iOS (по желанию): ntf-server.ini.example, init-ntf.sh,
│               build-ntf-server.sh, patches/
├── coturn/     → hearthd/deploy/coturn/turnserver.conf.tmpl (рендерится hearthd)
└── verify-ini-keys.sh
```

## 1. Откуда берутся бинари (ТЗ §6.1)

`latest` запрещён. Всегда конкретный тег + sha256 в `hearthd/manifest.toml`.

### GPG-подписей у релизов больше нет

Процедура ниже раньше строилась на файлах `.asc` рядом с бинарями. **Их нет.**
Проверено на `v7.0.1`: 25 артефактов в релизе, среди них ни одной подписи и ни одного
файла с контрольными суммами. Так же выглядят и соседние теги.

Значит `upstream.gpg_identity` в манифесте описывает намерение, а не выполнимую
проверку, и делать вид, что подпись сверена, нельзя.

Что осталось: **сверка одного и того же артефакта, скачанного двумя независимыми
сетевыми путями.** Это не заменяет подпись — она защищает от компрометации самого
GitHub, а это нет. Но MITM на одном канале такая сверка ловит, а больше здесь ловить
нечем.

**На машине с интернетом (НЕ на узле):**

```bash
TAG=v7.0.1                     # конкретный тег, `latest` запрещён
BASE=https://github.com/simplex-chat/simplexmq/releases/download/$TAG

for f in smp-server-ubuntu-22_04-x86-64 xftp-server-ubuntu-22_04-x86-64; do
    curl -fLO $BASE/$f
done
sha256sum smp-server-ubuntu-22_04-x86-64 xftp-server-ubuntu-22_04-x86-64
```

Те же файлы — со второй машины в **другой сети** (VPS, телефон на мобильном
интернете), и `sha256sum` обязан совпасть до символа. Расхождение = не переносить
файл на узел, разбираться.

Развёртывание 2026-09-09 (`fels`), для сверки при следующем обновлении:

```
e70a6d11312a91246e7c70ff42c7b7ab5c0f18f3905f4ef9d1bb33f810b5daa4  smp-server-ubuntu-22_04-x86-64
a597d2ab290ab97856b357e55464c557f02f2c39ccc408434930fe9f3b0713ec  xftp-server-ubuntu-22_04-x86-64
```

Дальше страховку берёт на себя манифест: `hearthctl manifest pin` записывает
измеренный хеш, и с этого момента `hearthd` ежечасно проверяет, что запущено ровно
то, что проверяли. Происхождение файла проверить нечем — а вот подмену **после**
установки поймает A12.

Перенос на узел: USB. После установки:

```bash
install -m 0755 smp-server-ubuntu-22_04-x86-64  /usr/local/bin/smp-server
install -m 0755 xftp-server-ubuntu-22_04-x86-64 /usr/local/bin/xftp-server

hearthctl manifest pin --name smp-server  --version $TAG
hearthctl manifest pin --name xftp-server --version $TAG
```

С этого момента `hearthd` считает sha256 каждый час; несовпадение = стоп релея и
critical-алерт (ТЗ §7.3, A12).

**Альтернатива — сборка из исходников** по upstream-инструкции. Тогда в манифесте
`source = "built-from-source"`, а хеш всё равно пиннится: важно не происхождение, а то,
что запущено ровно то, что проверяли.

### ntf-server — только из исходников

Релизный `ntf-server-*` из того же тега не годится: команда Apple и bundle ID
приложения SimpleX зашиты в его код. `ntf/build-ntf-server.sh` собирает тот же тег с
патчем из `ntf/patches/` в закреплённом окружении и печатает sha256; дальше — тот же
перенос по USB и `hearthctl manifest pin --name ntf-server`. Процедура целиком —
[docs/runbook-ntf.md](../docs/runbook-ntf.md).

## 2. Инициализация (один раз на жизнь узла)

```bash
./smp/init-smp.sh        # создаёт CA, ключи, fingerprint, ini
./xftp/init-xftp.sh
./ntf/init-ntf.sh        # только если нужен push для iOS (ADR 0016)
```

Init создаёт **собственный CA релея** в `/etc/opt/simplex/`. Отпечаток этого CA —
часть адреса `smp://<fp>:<pass>@10.66.10.10:5223`, поэтому:

> Эти ключи переезжают с ПК на mini-PC. Именно они, а не железо, и есть «узел»
> (ТЗ §2.5, §10.2).

Пароли на создание очередей генерируются скриптом и кладутся в
`/etc/hearth/secrets/{smp,xftp}-create-password` (0600) — оттуда их читает `hearthd`
при сборке bundle.

У push-сервера пароля нет, а его адрес `ntf://<fp>@<host>:2053` вшивается в сборку
iOS-приложения. Поэтому `/etc/opt/simplex-ntf` переезжает с узлом так же, как CA
релеев: новый отпечаток ломает пуши у всех установленных сборок.

## 3. Ini-файлы: почему `.example`, а не готовые

Имена ключей в `smp-server.ini` менялись между версиями upstream, и ТЗ §6.2 прямо
говорит «имена ключей уточнить по версии». Поэтому здесь лежит **эталон намерений**, а
источник истины — файл, который сгенерировал `smp-server init` вашего пинованного тега.

Порядок такой:

1. `smp-server init ...` генерирует настоящий ini;
2. `./verify-ini-keys.sh /etc/opt/simplex/smp-server.ini smp/smp-server.ini.example`
   показывает, какие ключи из эталона отсутствуют или называются иначе;
3. правите настоящий ini под требования ТЗ §6.2, а `.example` — под реальные имена
   ключей вашей версии, и коммитите обе правки одним коммитом.

Требования ТЗ §6.2/§6.3, которые обязаны выполняться независимо от имён ключей:

| Требование | Зачем |
|---|---|
| store log включён | сообщения переживают рестарт узла (A7) |
| restore messages включён | после возврата питания очереди восстанавливаются |
| TTL сообщений 21 день | ограничение хранения; совпадает с окном ротации адреса (§10.5) |
| пароль на создание очередей | посторонний в WG не создаст очередь (A3) |
| notification server в smp-server выключен | push-сервер — отдельная служба `ntf-server`, и только на узле с `[ntf]` (ADR 0016) |
| control port только 127.0.0.1 | health-check hearthd, снаружи недоступен |
| private message routing включён | релей не видит, кто с кем (§6.2) |
| information page — минимум | требование AGPL, без реальных имён |
| транспортные логи — минимум, без IP | §3.1: метаданные не накапливаем |
| bind только 10.66.10.10 | A1: никаких 0.0.0.0 |

## 4. Обновление (ТЗ §10.6)

1. Прочитать changelog: upstream периодически режет совместимость старых версий.
2. **Сначала клиенты, потом релей.**
3. Тестовое устройство — сутки на новой версии.
4. Новые хеши в `hearthd/manifest.toml` — тем же коммитом, что и обновление.
5. Security-релиз должен попасть в контур за ≤ 7 дней (ТЗ §1.4).
6. ntf-server: патч из `ntf/patches/` переносится на новый тег вручную — он маленький,
   но его контекст в `APNS.hs` может сдвинуться. `git apply --check` в
   `build-ntf-server.sh` остановит сборку, если это случилось.
