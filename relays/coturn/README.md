# coturn

Шаблон конфигурации живёт в `hearthd/deploy/coturn/turnserver.conf.tmpl` — так требует
структура Приложения A ТЗ (`hearthd/deploy/` содержит `coturn.conf`).

`/etc/turnserver.conf` **генерируется** демоном `hearthd` из шаблона при каждой ротации
статического секрета (ТЗ §6.4 — раз в месяц):

```bash
hearthctl rotate turn-secret
```

Править `/etc/turnserver.conf` руками бессмысленно: следующая ротация перезапишет файл.
Правьте шаблон `/etc/hearth/templates/turnserver.conf.tmpl`.

Ключевые решения (обоснование — прямо в шаблоне):

- **`no-tcp`** — ТЗ §6.4. Звонки идут по UDP внутри WireGuard, который уже даёт
  шифрование и аутентификацию транспорта; TLS/DTLS здесь добавил бы второй, отдельно
  управляемый сертификат без выигрыша.
- **`use-auth-secret` + ротируемый секрет** вместо статических пользователей: клиент
  получает короткоживущий credential в составе bundle, сам секрет узел не отдаёт.
- **`denied-peer-ip` на весь интернет + `allowed-peer-ip` только `10.66.0.0/16`** —
  TURN по определению форвардер пакетов, то есть потенциальный канал egress. nftables
  это уже запрещает, но замок должен быть и внутри coturn.
- **Публичных STUN в контуре нет вообще.** Клиент, ушедший на `stun.l.google.com`,
  раскрыл бы свой реальный адрес третьей стороне (ТЗ §6.4). Поэтому bundle содержит
  ровно два ICE-сервера, оба — наш узел, а acceptance-тест A8 проверяет, что среди
  ICE-кандидатов только `10.66.x.x`.
