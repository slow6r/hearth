# coturn

Шаблон конфигурации живёт в `hearthd/deploy/coturn/turnserver.conf.tmpl` — так требует
структура Приложения A ТЗ (`hearthd/deploy/` содержит `coturn.conf`).

`/etc/turnserver.conf` **генерируется** демоном `hearthd` из шаблона при каждой ротации
статического секрета (ТЗ §6.4 — раз в месяц):

```bash
hearthctl rotate turn-secret
```

Править `/etc/turnserver.conf` руками бессмысленно: следующая ротация перезапишет файл.
Правьте шаблон `/etc/hearth/templates/turnserver.conf.tmpl`.

Ключевые решения (обоснование — прямо в шаблоне):

- **TURN публичен по необходимости.** Когда оба собеседника за NAT (два телефона в
  мобильных сетях — обычный случай), медиапоток идёт только через релей. TURN, доступный
  лишь изнутри дома, для этого бесполезен.
- **`use-auth-secret` + ротируемый секрет** вместо статических пользователей: клиент
  получает короткоживущий credential в составе bundle, сам секрет узел не отдаёт.
- **`denied-peer-ip` на все приватные диапазоны** —
  TURN по определению форвардер пакетов. На публичном сервере это даёт две возможности:
  дотянуться в домашнюю сеть и бомбить третьи стороны. Обе закрыты списком запретов.
- **Публичных STUN в контуре нет.** Клиент, ушедший на `stun.simplex.im`,
  раскрыл бы свой адрес третьей стороне. Поэтому bundle содержит
  только наши ICE-серверы, а acceptance-тест A8 проверяет, что среди
  ICE-кандидатов только наш `node.host`.
