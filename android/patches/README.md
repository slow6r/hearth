# Серия патчей поверх upstream

**Правило (ТЗ §8.1):** каждое изменение — отдельный коммит поверх тега upstream, чтобы
`git rebase` на новый тег был механическим. Целевой размер диффа — **< 500 строк**, из
них **0 в Haskell**.

Порядок коммитов фиксирован: сначала то, что переживает любой рефакторинг upstream

## Как это работает

Здесь лежат **описания** патчей, а не `.patch`-файлы. Причина простая: точные имена
файлов и символов upstream меняются между тегами, и `.patch` с фиксированными
контекстами протух бы к первому же обновлению. Описание фиксирует **намерение и точку
интеграции**, а `git rebase` разрешает конфликт по существу.

Каждый файл описания содержит:

1. **Что делаем** — одним абзацем.
2. **Почему** — ссылка на пункт ТЗ. Если пункта нет, изменения быть не должно.
3. **Точка интеграции** — какой символ/экран правим и как его найти в текущем теге
   (`rg`-запрос, а не путь: путь протухает быстрее).
4. **Проверка** — какой acceptance-тест ловит регресс.

## Что запрещено (ТЗ §8.3)

- Любой diff в Haskell.
- Изменение формата `smp://`-адресов, рукопожатия, парсеров.
- Любые SDK: аналитика, крэш-репорты, FCM, Play Services.
- Переверстка upstream-экранов ради вкуса: каждый переписанный экран удорожает ребейз
  (ТЗ §8.5).

Проверяется скриптом `../scripts/verify-apk.sh` (A5) и ревью диффа:
`git diff <upstream-tag>..HEAD --stat` не должен содержать `.hs`.
