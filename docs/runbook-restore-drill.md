# Runbook: квартальная проверка восстановления

ТЗ §10.7, acceptance-тест A11.

Бэкап, который никогда не восстанавливали, — это не бэкап, а надежда. Раз в квартал,
по календарю.

## Что проверяем

1. age-ключ на месте и **читается** (не «лежит где-то», а реально расшифровывает);
2. архив целый и полный;
3. из него поднимается работающий релей;
4. store log доставляет сообщения (то есть переписка действительно переживает потерю
   узла).

## Порядок

### 1. Взять свежий архив

```bash
hearthctl backup list                 # архивы в спуле, новейший первым
# либо с hearth-backup:
ssh hearth-backup ls -la /srv/hearth-backup/
```

### 2. Посмотреть содержимое, не разворачивая

```bash
hearthctl backup restore <архив> --identity /media/usb/age-key.txt --into /tmp/x --list
```

Ожидаемо: `etc/opt/simplex/...` (CA и ключи), `var/opt/simplex/...` (store log),
`etc/hearth/...` (реестр устройств, PKI), `var/lib/hearth/...` (журналы и история).

Уже на этом шаге ловятся две частые беды: не тот ключ и не все каталоги в `backup.paths`.

### 3. Развернуть на чистой VM

VM внутри LAN, **альтернативный адрес и порты**, чтобы не столкнуться с
боевым узлом.

```bash
sudo hearthctl backup restore <архив> \
     --identity /media/usb/age-key.txt --into /
# адрес в конфиге релея и в hearthd.toml поменять на тестовый
systemctl start smp-server
```

### 4. Тестовый клиент

Отдельный профиль на запасном телефоне или desktop-клиенте: подключиться к тестовому
релею, отправить и получить сообщение.

Если store log восстановился — сообщения, лежавшие в очередях на момент бэкапа,
доставятся. Это и есть A11.

### 5. Прибрать и записать

VM уничтожить (в ней настоящие ключи CA!). В журнал:

```
2026-09-07  restore drill  архив hearth-hearth-node-20260906T030000Z.tar.gz.age
            расшифровка OK, релей поднялся, тестовое сообщение доставлено
            замечания: —
```

## Приёмник hearth-backup

Ночная задача делает на приёмнике две вещи: кладёт архив (`rsync`) и спрашивает у него
sha256 положенного файла (`ssh ... sha256sum`). Обе обязаны быть разрешены ключу
`/etc/hearth/secrets/backup_ed25519`.

Если ключ в `authorized_keys` ограничен через `command="rsync ..."` — обычная и
правильная практика, — то `sha256sum` там не выполнится, и узел будет получать
предупреждение «внешнюю копию не удалось сверить» каждую ночь, а `hearthctl status` —
вечный `Degraded` при полностью исправном бэкапе. Выходов два, оба делаются руками с
правами root и не требуют работающего hearthd.

**1. Разрешить обе команды (так правильнее).** В `~hearth-backup/.ssh/authorized_keys`
вместо `command="rsync ..."` поставить разборщик:

```
restrict,command="/usr/local/bin/hearth-backup-recv" ssh-ed25519 AAAA... hearth-node
```

```sh
#!/bin/sh
# /usr/local/bin/hearth-backup-recv — принимаем ровно две команды узла и ничего больше.
set -eu
case "${SSH_ORIGINAL_COMMAND:-}" in
    "rsync --server"*)                   exec $SSH_ORIGINAL_COMMAND ;;
    "sha256sum -- /srv/hearth-backup/"*) exec $SSH_ORIGINAL_COMMAND ;;
    *) echo "hearth-backup: команда не разрешена" >&2; exit 2 ;;
esac
```

**2. Не сверять хеш.** В `/etc/hearth/hearthd.toml`:

```toml
[backup.remote]
verify_digest = false
```

Тогда подтверждением служит только код возврата rsync, и статус узла говорит об этом
прямо — строка под «внешняя копия» читается «sha256 не сверяется». Это слабее: rsync не
отличает «копия доехала» от «копия доехала испорченной». Правка вступает в силу с
`systemctl restart hearthd`.

### Прореживание внешней копии

Внешняя копия не зеркалируется: голый `rsync --delete` сделал бы `/srv/hearth-backup`
производным от локального спула, и чистый спул после переустановки узла стёр бы всю
внешнюю историю. Но и не удалять ничего — тоже отказ, только отложенный: каталог растёт,
место кончается, и однажды свежий архив просто перестаёт приниматься. Поэтому ночная
задача удаляет ТОЛЬКО просроченные архивы этого узла:

- маска `hearth-<имя узла>-*.tar.gz.age` объявлена удаляемой, всё остальное в каталоге
  защищено правилом `--filter=P *` — чужие архивы, ключи, что угодно;
- удаление идёт после передачи (`--delete-after`): свежий архив доезжает в любом случае;
- за прогон исчезает не больше `backup.remote.max_delete` файлов (по умолчанию 3).
  Попытка превысить — код возврата rsync 25, то есть громкая жалоба, а не тихая потеря.

**Чего маска НЕ закрывает.** Она накрывает ровно собственные архивы узла — это и есть
предмет прореживания. Поэтому от сценария «узел переустановили, спул пуст, а на
приёмнике лежит история» защищает не маска, а только `max_delete`: за одну ночь уйдёт не
больше трёх файлов, но за пять ночей подряд уйдёт вся история, каждую ночь с кодом 25 и
предупреждением. **Перед переустановкой узла** (и вообще перед любым обнулением спула)
поставьте `max_delete = 0` и верните значение обратно, когда спул наполнится.

**Код 25 — не провал внешней копии.** Удаление идёт после передачи, поэтому 25 означает
«свежий архив доехал, каталог не прорежен»: `remote_ok` остаётся `true`, а в
`remote_note` и в алертах появляется строка «прореживание остановлено пределом
backup.remote.max_delete». Так бывает после двух-трёх пропущенных ночей, когда
просроченных архивов накопилось больше предела; само это не рассасывается — уберите
лишнее на приёмнике или поднимите предел.

Выключить прореживание целиком: `max_delete = 0` в `[backup.remote]`. Это обязательный
шаг, если приёмник запрещает удаление (`rrsync -no-del`) или ротирует копии сам, — иначе
rsync будет завершаться ошибкой каждую ночь. Следить за местом на `/srv/hearth-backup`
тогда обязан приёмник.

## `hearthctl health` и вердикт по бэкапу

Вердикт по резервной копии входит в общий `state` узла, но **не выше `Degraded`**:
`GET /health`, `hearthctl health` и внешний контроль видят `degraded` даже при живых
релеях, если успешного бэкапа не было дольше 48 часов. Зелёным узел без бэкапа не
бывает, но и `down` — не про него: `down` снаружи читается как «семья без связи», и
будить по нему дежурного ночью из-за не доехавшего архива значит приучить не смотреть
на красное. Полный вердикт (`Down`) остаётся в отдельном поле `backup` — его печатают
и `hearthctl health` строкой `backup=`, и `hearthctl status`, и `GET /backup/status`.

Следствие для нового узла: пока ночная задача не отработала ни разу, общий `state` —
`degraded`, а `backup=Down`. Чинить релеи тут нечего — нужно сделать первый бэкап:
`hearthctl backup now` (или дождаться 03:00 UTC).

## Красные флаги

| Симптом | Что это значит |
|---|---|
| age-ключ не нашёлся с первого раза | Он не «где-то есть» — найдите и зафиксируйте место, включая второй экземпляр (ТЗ §14) |
| В архиве нет `var/lib/hearth` | `backup.paths` урезали; история инцидентов не переживёт переезд (ADR 0006) |
| Архив старше суток | Ежедневный бэкап не идёт — смотреть `hearthctl backup status` и алерты |
| `remote_ok: false` при настроенном `[backup.remote]` | Внешняя копия НЕ подтверждена. Причина — строкой ниже в `hearthctl status` (поле `remote_note`): rsync не прошёл, hearth-backup вернул другой sha256 или приёмник не дал выполнить `sha256sum` (см. «Приёмник hearth-backup»). Пока копия не подтверждена, архив есть только на самом узле, а пожар и кража уносят и узел, и бэкап |
| `state` бэкапа не `Ok` в `hearthctl status` | Вердикт считается при каждом чтении: `Down` — это провал прогона, отсутствующий **обязательный** источник (`backup.required_paths`) или успех старше 48 часов; `Degraded` — бэкап выключен в конфигурации или внешняя копия не подтверждена |
| В `hearthctl status` есть блок «НЕТ НА ДИСКЕ» | Настроенный источник отсутствует на диске. Строки с пометкой **ОБЯЗАТЕЛЬНЫЙ** (они же в поле `missing_required`) проваливают прогон: архива за эту ночь нет. Остальные — например каталоги push-сервера на узле без push, которых в `required_paths` нет намеренно, — прогон проходит, вердикт не меняется, но факт остаётся на экране: настроенный источник исчез, и это либо так и задумано, либо размонтированный каталог |
| Непустой `unreadable`, кроме `/etc/hearth/pki/ca.key` | Дыра в архиве. Терпимые исключения перечислены поимённо в `backup.tolerated_unreadable`; всё остальное внутри `required_paths` проваливает запуск |
