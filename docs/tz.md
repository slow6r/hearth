## 0. Границы стека

| Слой | Технология | Что делаем |
|---|---|---|
| Криптопротокол, релеи SMP/XFTP | Haskell (upstream) | **Не трогаем.** Стоковые бинари, pinned версия, проверенные подписи |
| Обвязка узла (`hearthd`) | **Rust** | Новый код, у которого нет «предшественника» — переход бесплатен. Supervisor, egress-watchdog, бэкапы, генерация клиентских конфигов, admin API |
| Android-клиент | **Kotlin** | Конфиг-форк upstream: пресеты, брендинг, дефолты безопасности. Haskell-ядро клиента не трогаем |
| iOS-клиент | Swift (upstream) | Фаза 2. До неё — стоковое приложение с ручным конфигом |

**Правило для Rust:** пишем на нём только то, чего в SimpleX нет и не было. Ни одна существующая строка upstream не переписывается ни на Rust, ни на что-либо ещё. Если для задачи достаточно systemd-юнита и 20 строк shell — это допустимо на фазе 0, `hearthd` заменяет их на фазе 1.

## 1. Цель и границы

### 1.1 Цель
Приватный канал связи для закрытого круга (семья, ≤ 20 устройств), полностью на собственном домашнем железе, не зависящий от публичных релеев, магазинов приложений, номеров телефонов и push-инфраструктуры Google/Apple. Клиенты подключаются к домашней сети через существующий семейный WireGuard/AmneziaWG на UDM Pro.

### 1.2 Не цель
- Публикация где угодно (App Store, Google Play, RuStore, публичный F-Droid).
- Федерация с публичной сетью SimpleX. Чужие релеи выключены, свои не анонсируются.
- Изменение протокола, форматов сообщений, крипты, логики очередей.
- Любые серверы вне дома — ни релей, ни резерв, ни бэкап.
- Мультиаккаунт, боты, каналы, публичные группы.

### 1.3 Фазы
| Фаза | Узел | Срок |
|---|---|---|
| 0 | Релеи на существующем ПК (Linux-VM или bare metal) | старт → покупка mini-PC |
| 1 | Переезд на выделенный mini-PC **без смены адреса релея** | 1 вечер |
| 2 | iOS-форк, сборка Haskell-ядра из исходников, reproducible builds | по желанию |

### 1.4 Критерии успеха
1. Ни один байт трафика мессенджера не покидает домашнюю сеть + WG (проверяется nftables-счётчиками, §5.4).
2. Переезд ПК → mini-PC: клиенты не замечают, ни одного действия на устройствах.
3. Новое устройство подключается за ≤ 5 минут по одному QR.
4. Security-релиз upstream попадает в контур ≤ 7 дней.

## 2. Принципы

1. **Verify, don't trust.** Доверие к бинарю заменяется наблюдением за сетью. Релей физически не может отправить данные наружу.
2. **Логика upstream неприкосновенна.** Любой diff к Haskell-коду — блокер ревью. Меняем только конфиги, пресеты, ресурсы, UI-слой Kotlin.
3. **Минимум состояния на сервере.** Релей — тупая труба: шифроблоб принял, отдал, удалил.
4. **Всё внутри дома и WG.** Нет публичных портов, нет DNS, нет исходящих соединений с узла.
5. **Адрес релея — константа.** IP, CA и пароль живут дольше железа. Железо меняется, адрес — нет.
6. **Один источник правды по версиям.** Всё pinned по тегу + sha256. `latest` запрещён.

## 3. Модель угроз

### 3.1 Защищаемся от
| Угроза | Мера |
|---|---|
| Пассивный наблюдатель на канале (провайдер, DPI) | Трафик — внутри WG/AWG до UDM Pro; для DPI мессенджер не существует как класс |
| Компрометация узла | Релей не хранит ключей контента; egress-watchdog заметит утечку; store log — только зашифрованные очереди |
| Подмена ключей сервера (MITM) | Отпечаток CA сервера зашит в адрес `smp://<fp>:<pass>@host:port`, клиент отвергает несовпадение |
| Захват релея посторонним в WG | Пароль на создание очередей + вход только из WG/LAN-подсети |
| Утеря/кража телефона | Биометрия, FLAG_SECURE, исчезающие сообщения по умолчанию, удаление контакта остальными |
| Утечка через бэкапы ОС | `allowBackup=false`, исключение из Google/iCloud backup |
| Утечка метаданных через пуши | Push-серверы отключены; доставка через постоянное соединение внутри WG |
| Физический доступ к узлу (кража ПК/mini-PC) | LUKS на диске; ключи релея внутри LUKS; без диска содержимое бесполезно |

### 3.2 Не защищаемся от
- Малварь на устройстве с root/jailbreak.
- Физическое принуждение владельца устройства.
- Уязвимости нулевого дня в протоколе SimpleX (снижаем только скоростью апгрейда).
- Отключение электричества/интернета дома (принятый риск, см. §14).

## 5. Сетевой контур

### 5.1 Адресация
- WG-подсеть: `10.66.0.0/16` (существующая).
- `10.66.10.0/24` — инфраструктура дома, `10.66.100.0/24` — клиентские устройства.
- Релеи биндятся **только** на `10.66.10.10`. Этот IP закрепляется за узлом статически на UDM Pro (DHCP reservation по MAC для фазы 0, затем перепривязка на MAC mini-PC при переезде).
- На `0.0.0.0` — нельзя, проверяется в acceptance-тестах.

### 5.2 DNS
- На узле нет резолвера. `/etc/resolv.conf` пустой, `systemd-resolved` выключен.
- Клиенты используют IP напрямую в `smp://` строке. Имён нет — нечего перехватывать.

### 5.3 Firewall узла (nftables)
```
table inet hearth {
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ct state established,related accept
    ip saddr 10.66.0.0/16 tcp dport { 5223, 5443 } accept
    ip saddr 10.66.0.0/16 udp dport 3478 accept
    ip saddr 10.66.0.0/24 tcp dport 7443 accept        # admin API
    ip saddr 10.66.0.0/24 tcp dport 22 accept          # ssh, только ключи
    counter log prefix "hearth-in-drop " drop
  }
  chain output {
    type filter hook output priority 0; policy drop;
    oif lo accept
    ct state established,related accept
    ip daddr 10.66.0.0/16 accept
    counter log prefix "hearth-egress-drop " drop      # ← детектор утечек
  }
}
```
На фазе 0 в VM правила те же; на хосте-ПК дополнительно: VM в bridged-режиме на отдельный VLAN, чтобы хостовая ОС не была её маршрутом.

### 5.4 Egress-контроль как детектор
`hearth-egress-drop` — единственное место, куда упадёт любая попытка «позвонить домой». `hearthd` читает счётчик и лог (§7.3). Ожидаемое значение за сутки — **0**. Иное — инцидент.

### 5.5 TLS
- SMP/XFTP используют собственный CA, генерируемый при `smp-server init`. Отпечаток CA — часть адреса сервера. Публичный CA не нужен.
- Ключи CA в `/etc/opt/simplex/`, бэкапятся шифрованно (§7.3). **Именно они переезжают с ПК на mini-PC** — это и сохраняет адрес неизменным.

## 6. Релеи (upstream, без изменений)

### 6.1 Версионирование
- Ветка `stable`, конкретный тег. `latest` запрещён.
- Бинарь: сборка из исходников по upstream-инструкции **или** релизный бинарь с проверкой GPG-подписи `chat@simplex.chat` и sha256. Хэш — в манифесте `hearthd`.
- Docker — только со своим образом из pinned Dockerfile. На фазе 0 предпочтителен bare-бинарь под systemd: меньше слоёв, проще перенос.

### 6.2 smp-server — целевая конфигурация
Инициализация: `smp-server init -y -l --ip 10.66.10.10 --password <pass>` (флаги сверить с pinned версией).

Требования к `smp-server.ini` (имена ключей уточнить по версии):
- **store log** — включён.
- **restore messages** — включён.
- **TTL сообщений** — 21 день.
- **пароль на создание очередей** — обязателен.
- **новые очереди** — разрешены.
- **notification server** — выключен.
- **information page** — минимум (требование AGPL), без реальных имён.
- **control port** — `127.0.0.1` only, для health-check `hearthd`.
- **private message routing** — включён (релей ≥ 5.8).
- Транспортные логи — выключены или минимум, ротация 7 дней, без IP клиентов.

### 6.3 xftp-server
- Порт 5443 на `10.66.10.10`. Квота 32 ГБ, файл до 1 ГБ (upstream-лимит), TTL 7 дней. Пароль на загрузку, control port локально.

### 6.4 coturn
- `listening-ip=10.66.10.10`, `relay-ip=10.66.10.10`, `no-tcp`, long-term credentials, статический секрет ротируется `hearthd` раз в месяц.
- Публичные STUN/TURN у клиентов **удалены** — иначе клиент может уйти на чужой TURN.

### 6.5 Резервирование
Второго релея **нет** — по дизайну, чтобы не тащить внешние серверы. Последствие: узел выключен → сообщения копятся на клиентах и доставляются при возврате. Для семьи это приемлемо. Если позже захочется резерв — вторая машина дома с собственным CA и адресом, включённая в клиентах **с первого дня** (upstream не переносит существующие контакты между релеями автоматически).

## 7. Control plane `hearthd` (Rust)

### 7.1 Назначение
Единственный компонент, который пишем сами. Управляет узлом, ничего не знает о сообщениях, не имеет исходящих соединений за пределы `10.66.0.0/16`.

### 7.2 Стек
- `tokio`, `axum` (admin API), `rustls` (mTLS), `serde`/`toml`, `age` (бэкапы), `nft -j` (JSON) для nftables, `systemctl` через `zbus`, `tracing` → journald.
- Никаких HTTP-клиентов наружу. `cargo deny` в CI: лицензии, advisories, дубли. Аудит `cargo tree` на сетевые зависимости.
- Один статический бинарь (`musl`), пользователь `hearth`, `CAP_NET_ADMIN` только для чтения nft.

### 7.3 Модули

**supervisor** — следит за юнитами `smp-server`, `xftp-server`, `coturn`; health через TCP на WG-порт + control port; рестарт с backoff; алерт при ≥ 3 падениях за 10 мин.

**egress-watchdog** — раз в 30 с читает счётчики `hearth-egress-drop` / `hearth-in-drop`, парсит journald по префиксам, агрегирует по `daddr:dport`. Любой ненулевой egress-drop → `critical`, в истории навсегда. Раз в 5 мин `ss -tnp`: established-сокет релея с не-WG адресом → `critical`.

**integrity** — при старте и раз в час sha256 бинарей против манифеста. Несовпадение → стоп релея + алерт.

**backup** — раз в сутки `tar` из `/etc/opt/simplex` (CA, ключи) + `/var/opt/simplex` (store log) → `age` публичным ключом владельца → rsync на `hearth-backup` (10.66.10.20). Приватный `age`-ключ хранится **вне** узла (YubiKey/оффлайн). Ретеншн 14 суток. Проверка восстановления — квартально (§10.6).

**config-gen** — список устройств (`device_id`, имя, дата); генерирует bundle (Приложение B) в JSON + QR PNG. QR отдаётся только через admin API внутри WG, никуда не сохраняется.

**admin API** (`:7443`, mTLS, клиентские сертификаты от собственного CA `hearthd`): `GET /health`, `/alerts`, `/egress`, `/devices`, `POST /devices`, `GET /devices/{id}/bundle.png`, `POST /rotate/turn-secret`, `POST /backup/now`, `GET /migrate/export` (см. §10.2). Веб-UI в v1 нет; CLI `hearthctl`.

**alerts** — журнал + WG-only Gotify на UDM Pro или бипер по GPIO. Внешние каналы (Telegram-бот, e-mail) запрещены.

### 7.4 Что `hearthd` никогда не делает
- Не читает store log содержательно.
- Не логирует адреса клиентов.
- Не имеет автообновления.

### 7.5 Фаза 0 без `hearthd`
Допустимо стартовать на systemd-юнитах + `nft` + cron-скрипте бэкапа, чтобы не блокировать запуск релеев разработкой обвязки. `hearthd` вводится до переезда на mini-PC — процедура миграции §10.2 должна идти через него.

## 8. Android-клиент (Kotlin, конфиг-форк)

### 8.1 Стратегия
- Форк `simplex-chat/simplex-chat`, отслеживание тегов `stable`.
- Haskell-ядро (`.so`) — в v1 **не собираем**: релизные библиотеки upstream с проверкой хэша. Своя сборка — фаза 2.
- Все изменения — отдельными коммитами поверх upstream-тега, чтобы `git rebase` был механическим. Целевой diff < 500 строк, из них 0 в Haskell.
- Security-тег upstream → rebase, сборка, раскатка за ≤ 7 дней.

### 8.2 Разрешённые изменения
1. **Пресеты серверов.** Заменить upstream-операторов и `smp*.simplex.im` / `xftp*.simplex.im` на `10.66.10.10`. Модуль пресетов в shared Kotlin (`apps/multiplatform/common`), точное имя сверить по тегу.
2. **Операторы сети.** Экран выбора операторов — скрыть.
3. **ICE-серверы.** Дефолт — наш coturn; публичные STUN удалены.
4. **Notification server** — отключён; режим доставки `Instant` (foreground-сервис); Periodic/Push недоступны в UI.
5. **Приватный роутинг** — включён по умолчанию.
6. **Дефолты безопасности:** `allowBackup="false"`, запрещающие `dataExtractionRules`; `FLAG_SECURE` без возможности выключить; биометрия при первом запуске; исчезающие сообщения 7 дней для новых контактов (пресет на уровне контакта/группы или пункт онбординга); превью в шторке — только «Новое сообщение».
7. **Онбординг.** Первый экран: «Отсканируй QR настройки узла» → импорт bundle. Далее стандартный upstream-онбординг профиля.
8. **Брендинг.** Имя, иконка, `applicationId`, тема. Экран «О программе» — ссылка на upstream и AGPLv3 (обязательно).
9. **Обновления.** In-app проверка отключена. Канал — собственный F-Droid-репозиторий на `hearth-node` (только из WG). Fallback — APK через сам мессенджер с проверкой подписи.

### 8.3 Запрещённые изменения
- Любой diff в Haskell.
- Изменение формата `smp://`-адресов, рукопожатия, парсеров.
- Любые SDK: аналитика, крэш-репорты, FCM, Play Services. `apkanalyzer` проверяет отсутствие `com.google.android.gms`.

### 8.4 Сборка и подпись
- Ключ подписи — оффлайн, hardware-backed (YubiKey/`pkcs11`), в CI отсутствует; подпись — ручной шаг.
- Версии JDK/AGP/Gradle/NDK зафиксированы в `gradle/libs.versions.toml`. Reproducible build — фаза 2.
- Только `arm64-v8a` (+ `x86_64` для эмулятора в debug).

### 8.5 UI
- Кастомизация ограничена темой и онбордингом. Переверстывать upstream-экраны в v1 — нет: каждый переписанный экран удорожает rebase.
- Тема — отдельный модуль, не размазана по upstream-файлам. Без generic-градиентов, «домашний» тон.

## 10. Операционные процедуры

### 10.1 Фаза 0: узел на ПК
- **Не** запускать релей на хостовой Windows/Docker Desktop: нет контроля egress, нет LUKS, спящий режим убивает доставку.
- Вариант A (предпочтительный): ПК целиком под Debian minimal.
- Вариант B: KVM/Hyper-V VM с Debian, bridged NIC на отдельный VLAN, статический `10.66.10.10`, автозапуск VM при старте хоста, `hibernate/sleep` на хосте отключены.
- Диск VM/ПК — LUKS, ключ на USB-токене или TPM с PIN.
- С первого дня всё лежит в трёх каталогах: `/etc/opt/simplex`, `/var/opt/simplex`, `/etc/hearth`. Ничего вне них — иначе переезд станет ручным.

### 10.2 Переезд ПК → mini-PC (без смены адреса)
1. mini-PC: Debian, LUKS, nftables из `hearthd/deploy`, тот же pinned бинарь релея (sha256 совпадает с манифестом).
2. На UDM Pro: DHCP reservation `10.66.10.10` переносится на MAC mini-PC, **пока старый узел ещё работает**.
3. На ПК: `hearthctl migrate export` → останавливает релеи, делает финальный tar трёх каталогов, age-шифрует, кладёт на `hearth-backup`.
4. На mini-PC: `hearthctl migrate import <file>` → расшифровка (оффлайн-ключ у владельца), раскладка, проверка sha256 бинарей, запуск.
5. Старый узел — выключен и **не** включается снова с теми же ключами (конфликт адреса + два релея с одним CA).
6. Проверка: с телефона отправить сообщение, проверить `hearthctl health`. Клиенты ничего не делают — адрес `smp://<fp>:<pass>@10.66.10.10:5223` не изменился.
7. Диск ПК — `cryptsetup luksErase` или физическое удаление раздела.

### 10.3 Добавление устройства
1. `hearthctl device add "Мама — Pixel 8"` → QR.
2. Устройство в семейном WG (существующая процедура).
3. APK из внутреннего F-Droid.
4. Скан QR → серверы прописаны.
5. Обмен контактами — **только лично**: одноразовая ссылка/QR при встрече, не через другие мессенджеры.
6. Добавление в семейную группу существующим участником.

### 10.4 Утеря устройства
1. Остальные удаляют контакт/участника — очереди на релее инвалидируются.
2. `hearthctl device revoke <id>`.
3. WG-пир удаляется на UDM Pro.
4. Подозрение на извлечение пароля релея → ротация адреса (§10.5).

### 10.5 Ротация адреса релея
Только внеплановая (компрометация CA/пароля). Новый init рядом на другом IP → bundle всем → каждый контакт вручную «Change receiving address» → старый релей выключается через 21 день (TTL).

### 10.6 Обновление компонентов
1. Новый тег → changelog, особенно совместимость релеев и клиентов (upstream периодически режет старые версии).
2. Сначала клиенты, потом релей.
3. Тестовое устройство сутки на новой версии.
4. Хэши в манифесте `hearthd` — в том же коммите.

### 10.7 Проверка восстановления (квартально)
VM внутри LAN → расшифровать бэкап оффлайн-ключом → релей на альтернативном IP → тестовый клиент → сообщение. Результат в журнал.

## 11. Железо

| Роль | Фаза 0 | Фаза 1 |
|---|---|---|
| `hearth-node` | Существующий ПК: Debian bare metal или KVM-VM; LUKS; sleep выключен; проводом в UDM Pro | Mini-PC x86-64 (N100/N305, HP t630 и т.п.), 8–16 ГБ, NVMe 256 ГБ LUKS, Wi-Fi/BT отключены в BIOS, проводом |
| ОС | Debian stable minimal. `unattended-upgrades` **выключен** (у узла нет egress); security-обновления — вручную через `apt-offline`/USB или временный allow-list в nft на зеркало Debian, снимаемый после | то же |
| `hearth-backup` | Любая вторая машина дома / NAS / USB-диск на UDM Pro, доступна по SSH в `10.66.10.20` | то же |
| Питание | Желателен UPS | UPS ≥ 30 мин, `nut` → корректный shutdown |

## 14. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Единственный узел дома: нет света/интернета → нет связи | Средняя | Принято по дизайну; UPS; сообщения копятся на клиентах и доходят позже |
| Домашний IP/канал провайдера: WG к дому заблокирован DPI | Средняя | AWG уже используется; при необходимости — обфускация на UDM Pro, релей не трогается |
| ПК на фазе 0 используется как рабочая машина → перезагрузки, sleep | Высокая | Вариант A (bare metal) или жёсткие настройки хоста; быстрее переезжать на mini-PC |
| Upstream меняет структуру пресетов → rebase ломается | Средняя | Диф изолирован; A5–A6 ловят регресс |
| Upstream режет совместимость старого релея с новым клиентом | Средняя | Порядок §10.6 |
| WG-только доставка = нет VPN → нет мессенджера | Высокая (по дизайну) | Always-on VPN + kill-switch в Android |
| Утеря оффлайн `age`-ключа | Низкая | Второй экземпляр у другого взрослого |
| Регуляторные вопросы к ОРИ | Низкая для непубличного семейного контура | Ничего не публикуем; при сомнениях — юрист до старта |

## 15. Открытые вопросы
1. Фаза 0: ПК под Debian целиком или VM? Зависит от того, нужен ли ПК под что-то ещё.
2. Сколько устройств на iOS — приоритет фазы 2.
3. Что будет `hearth-backup`: NAS, второй ПК или USB на UDM Pro.
4. Канал алертов: Gotify на UDM Pro или бипер.

## Приложение B. Формат bundle для клиента

```json
{
  "v": 1,
  "smp":  ["smp://<fp1>:<pass1>@10.66.10.10:5223"],
  "xftp": ["xftp://<fp2>:<pass2>@10.66.10.10:5443"],
  "ice": [
    { "urls": ["stun:10.66.10.10:3478"] },
    { "urls": ["turn:10.66.10.10:3478"], "username": "<ts>:hearth", "credential": "<hmac>" }
  ],
  "net": { "privateRouting": "always", "presetsEnabled": false, "ntfMode": "instant" },
  "issued": "2026-09-06T12:00:00Z",
  "device": "mama-pixel8"
}
```

QR содержит JSON целиком (≤ 1 КБ). Пароли релеев — единственная чувствительная часть; QR показывается только внутри WG через admin API и не сохраняется в галерею.
