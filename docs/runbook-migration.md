# Runbook: переезд ПК → mini-PC без смены адреса

ТЗ §10.2. Критерий успеха (ТЗ §1.4 п.2): **клиенты не замечают переезда и не делают
ничего**.

**Время:** один вечер. **Репетиция обязательна** — acceptance-тест A13 требует прогнать
эту процедуру на тестовой VM до покупки mini-PC.

---

## Почему это вообще работает

Адрес релея `smp://<отпечаток CA>:<пароль>@<node.host>:5223` не содержит ничего,
привязанного к железу. Переезжают три вещи:

1. отпечаток CA и ключи — `/etc/opt/simplex`;
2. пароль на создание очередей — `/etc/hearth/secrets`;
3. публичное имя `node.host` — переставляется проброс портов на роутере.

Всё остальное (store log, реестр устройств, история инцидентов) едет тем же архивом,
чтобы новый узел был **тем же узлом**, а не только тем же адресом.

### Что НЕ переезжает: файлы XFTP

`/var/opt/simplex-xftp` — тела файлов «в полёте» — намеренно отсутствует в
`backup.paths`. Это сотни гигабайт транзитных данных с TTL 7 дней, и таскать их в
каждом ночном архиве бессмысленно.

Последствие для переезда: **файлы, отправленные, но ещё не забранные получателем,
пропадут.** Сообщения не пострадают — они в store log, который переезжает.

Что с этим делать:

- посмотреть, есть ли неотданные файлы: `ls /var/opt/simplex-xftp/files` на старом узле;
- если есть и они важны — попросить получателей открыть приложение и дождаться
  загрузки, потом делать экспорт;
- либо разово добавить каталог в `backup.paths` перед `migrate export` и убрать
  обратно после (архив разбухнет, но ничего не потеряется);
- либо принять потерю: отправитель увидит, что файл не дошёл, и пришлёт снова.

Для семейного контура третий вариант обычно правильный. Главное — решить осознанно,
а не обнаружить постфактум.

---

## Что понадобится

- [ ] mini-PC с установленным Debian, LUKS, статическим сетевым конфигом (пока с
      **временным** LAN-адресом — не тем, на который настроен проброс)
- [ ] офлайновый age-ключ (YubiKey или бумажная/USB-копия)
- [ ] клиентский сертификат админа
- [ ] доступ к роутеру (проброс портов)
- [ ] телефон для финальной проверки
- [ ] прогнанная репетиция A13

## Порядок

### 1. Подготовить mini-PC (старый узел ещё работает)

```bash
# те же шаги, что и на фазе 0, но БЕЗ инициализации релеев:
sudo ./hearthd/deploy/install.sh
nft -f /etc/hearth/nftables/hearth.nft
```

**Не запускать `smp-server init`.** Идентичность приезжает из архива; init создал бы
новый CA и сломал бы весь смысл переезда.

Положить те же pinned-бинари релеев (sha256 обязан совпасть с манифестом).

### 2. Переставить проброс портов (ТЗ §10.2 п.2)

На роутере: проброс 5223/443/5443/3478/49160-49200 переносится на LAN-адрес mini-PC —
**пока старый узел ещё работает**. Порядок именно такой: сделать это после выключения
старого узла — значит получить окно, когда узел не отвечает вообще.

Пока mini-PC живёт на временном LAN-адресе, конфликта нет.

### 3. Экспорт на старом узле

```bash
hearthctl migrate export
```

Что произойдёт:

- остановятся `smp-server`, `xftp-server`, `coturn` (store log не должен меняться во
  время копирования);
- соберётся один `tar.gz.age`, зашифрованный публичным age-ключом;
- напечатается путь, размер и **sha256** — записать его.

С этого момента мессенджер лежит. Дальше — быстро.

### 4. Перенести архив

По `hearth-backup` (`rsync` уже положил его туда) или USB. На mini-PC сверить хеш:

```bash
sha256sum hearth-migrate-*.tar.gz.age    # обязан совпасть с напечатанным
```

### 5. Импорт на mini-PC

```bash
sudo hearthctl migrate import \
    /path/to/hearth-migrate-<...>.tar.gz.age \
    --identity /media/usb/age-key.txt \
    --into / \
    --sha256 <хеш из шага 3>
```

Команда расшифрует архив офлайновым ключом, разложит каталоги, проверит sha256 бинарей
против приехавшего манифеста и напечатает оставшиеся шаги.

Если хеш не совпал — импорт откажется работать. Это не формальность: архив едет через
USB или чужую машину.

### 6. Перевести mini-PC на боевой адрес и стартовать

```bash
# боевой LAN-адрес в systemd-networkd, затем:
systemctl restart systemd-networkd
nft -f /etc/hearth/nftables/hearth.nft
systemctl enable --now smp-server xftp-server coturn hearthd
hearthctl health
```

### 7. Проверка с телефона (ТЗ §10.2 п.6)

Отправить сообщение члену семьи. На устройстве **не делается ничего** — адрес не менялся.

```bash
hearthctl health          # все сервисы ok
hearthctl egress          # egress_drop delta = 0, foreign sockets: none
hearthctl status
```

### 8. Похоронить старый узел (ТЗ §10.2 п.5, п.7)

```bash
# на старом узле
systemctl disable --now smp-server xftp-server coturn hearthd
```

> **Старый узел больше никогда не включается с этими ключами.** Два релея с одним CA и
> одним адресом — split brain, который клиент обнаружить не может: часть сообщений уйдёт
> в узел, которого для остальных не существует.

После того как новый узел отработал сутки без замечаний:

```bash
cryptsetup luksErase /dev/<раздел>     # либо физическое уничтожение носителя
```

## Репетиция (A13) — до покупки железа

Та же процедура, но `--into /srv/rehearsal` на тестовой VM:

```bash
hearthctl migrate export
hearthctl migrate import <архив> --identity <ключ> --into /srv/rehearsal --sha256 <хеш>
ls /srv/rehearsal/etc/opt/simplex/       # ca.key, fingerprint на месте
```

Затем на VM с альтернативным адресом поднять релей из восстановленных файлов и убедиться,
что тестовый клиент подключается. Результат — в журнал.

Репетиция стоит час. Незамеченная проблема в вечер переезда стоит вечера и нервов.

---

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Импорт: «archive sha256 mismatch» | Архив побился при переносе. Копировать заново, не «пробовать всё равно» |
| Импорт: «age decrypt (wrong key?)» | Не тот age-ключ. Правильный — у владельца офлайн |
| `hearthctl health`: сервис не слушает | Проверить `ip a` и что nft загружен |
| Клиенты не видят узел | Проверить проброс портов на роутере и что старый узел выключен |
| Хеши бинарей не сошлись | На mini-PC лежит другая сборка релея. Положить ровно ту, что в манифесте |
| **Всё плохо, надо назад** | Вернуть проброс на старый ПК, включить релеи там. Это работает, пока старый диск не стёрт — поэтому шаг 8 делается **через сутки**, а не сразу |
