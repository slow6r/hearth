# Runbook: ротация адреса релея

ТЗ §10.5. **Только внеплановая** — при компрометации CA или пароля релея.

Это самая дорогая процедура в контуре: каждый контакт у каждого члена семьи требует
ручного действия. Плановой ротации нет и не должно быть.

## Когда действительно нужно

- утёк или мог утечь пароль на создание очередей (`/etc/hearth/secrets/smp-create-password`);
- скомпрометированы ключи CA релея (`/etc/opt/simplex`) — например, украден диск без LUKS;
- узел был доступен постороннему с правами root.

**Не нужно** при: потере устройства с закрытым WG-доступом (достаточно §10.4), смене
железа (это §10.2 — там адрес как раз сохраняется), плановой гигиене.

## Порядок

### 1. Поднять новый релей рядом, на другом IP

Старый продолжает работать — иначе семья остаётся без связи на время процедуры.

```bash
# на узле, с другим адресом (например 10.66.10.11)
CONFIG_DIR=/etc/opt/simplex-new NODE_IP=10.66.10.11 ./relays/smp/init-smp.sh
```

Новый init создаёт **новый CA и новый пароль** — то есть новый адрес.

### 2. Раздать новый bundle

```bash
hearthctl device bundle <id>        # для каждого активного устройства
```

Показывать QR лично или по видеосвязи внутри WG. Не пересылать.

### 3. Каждый контакт — вручную

В клиенте SimpleX: для каждого контакта «Change receiving address» (сменить адрес
получения) на новый сервер. Это делает каждый член семьи у себя.

Пока часть контактов на старом адресе, а часть на новом — оба релея должны работать.

### 4. Выключить старый релей через 21 день

21 день — это TTL сообщений (ТЗ §6.2). Раньше выключать нельзя: недоставленные
сообщения, лежащие в старых очередях, пропадут.

```bash
systemctl disable --now smp-server-old
```

### 5. Прибрать

- удалить старые ключи CA;
- обновить `hearthd.toml` (адрес, пути к секретам);
- `hearthctl manifest verify`, `hearthctl health`;
- записать инцидент в журнал: что утекло, когда, что сделано.

## Почему это так неудобно

Адрес релея содержит отпечаток CA — именно это защищает от MITM (ТЗ §3.1). Обратная
сторона той же медали: сменить адрес = сменить идентичность сервера, и у клиента нет
способа принять новую идентичность автоматически, не открыв дыру ровно того размера,
которую отпечаток закрывает.

Неудобство здесь — не недоработка, а прямое следствие свойства, ради которого всё
строилось.
