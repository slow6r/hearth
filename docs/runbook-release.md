# Runbook: выпуск сборки и публикация обновления

Две подписи, и они разные. **Ключ APK** доказывает Android, что обновление от того же
автора, что установленное приложение. **Ключ манифеста** доказывает клиенту, что
список версий выпустили мы, а не захваченный узел. Оба лежат на рабочей станции, ни
один не копируется на узел.

Пропуск второй подписи не сломает установку — он сломает обновление у всех: сборка со
вшитым открытым ключом отказывается брать неподписанный манифест. Это осознанно: иначе
защиту выключал бы тот, от кого она защищает.

## 1. Подготовить дерево

```bash
cd android
scripts/bake-node.sh relay.myhearth.ru 7444   # адрес узла, CA, открытый ключ подписи
scripts/sync-overlay.sh                        # правки overlay → дерево форка
```

Закоммитить изменения **в форке** и перевыпустить патчи:

```bash
git -C simplex-chat add -A . && git -C simplex-chat commit
scripts/export-fork-patches.sh
```

Без этого сборка не пойдёт: `build-release.sh` отказывается собирать выпуск из
изменённого дерева. Так и задумано — именно этой проверки не хватило при выпуске
7.0.1-h15, когда APK ушёл людям, а исходники в git не попали, и аудит справедливо
спросил «из чего это собрано».

## 2. Собрать и подписать APK

```bash
scripts/build-release.sh
apksigner sign --ks ../keys/admin/hearth-release.jks --ks-key-alias hearth \
  --ks-pass file:<пароль> --key-pass file:<пароль> \
  --out hearth-<версия>.apk <собранный APK>
```

`apksigner` читает оба пароля из ОДНОГО файла последовательно, поэтому в файле должны
быть две строки с одним и тем же паролем. Иначе он падает с «end of file reached» —
это не ошибка ключа.

## 3. Проверить

```bash
scripts/verify-apk.sh hearth-<версия>.apk
```

Проверка падает от ошибки инструмента, а не проходит на пустом выводе. Она обязана
пройти целиком; «почти всё OK» означает, что сборку раздавать нельзя.

Сами проверки тоже проверяются: `scripts/tests/run.sh` гоняет их по фикстурам,
включая заведомо плохие (бэкап включён, сборка с отладкой, чужая подпись, секрет в
ресурсе).

## 4. Собрать и подписать манифест

```bash
sha256sum hearth-<версия>.apk
```

`manifest.json` — ровно эти поля:

```json
{
  "v": 1,
  "versionName": "7.0.1-h16",
  "versionCode": 387,
  "sha256": "<из sha256sum>",
  "file": "hearth-7.0.1-h16.apk",
  "issued": "<время выпуска, RFC 3339>",
  "notes": "<что изменилось, одной фразой для человека>"
}
```

`issued` обязано **расти**: клиент помнит самую свежую отметку и откажется от
манифеста старее. Это защита от заморозки — захваченный узел не может подсунуть своё,
но мог бы показывать старое.

```bash
hearthctl --config keys/admin/hearthd.toml release sign manifest.json --key keys/admin/release-sign.key
hearthctl --config keys/admin/hearthd.toml release verify manifest.json --pubkey keys/admin/release-sign.pub
```

Проверять подпись у себя обязательно: подписывается содержимое файла байт в байт, и
любая последующая правка манифеста — хоть пробел — делает подпись неверной.

## 5. Выложить

На узел, в `updates_dir` (по умолчанию `/srv/hearth/updates`), владелец
`hearth:hearth`, права `0640`:

```
hearth-<версия>.apk
manifest.json
manifest.json.sig
```

Предыдущий APK убрать: манифест указывает ровно на один файл.

`versionCode` обязан строго расти — по нему клиент решает, новее ли сборка, и по нему
же отказывается откатываться.

## 6. Раскатка

Сначала одно устройство, сутки (ТЗ §10.6 п.3). Потом остальные.

Проверить на устройстве: обновление предложено, установилось, приложение запускается,
сообщения ходят. Если обновление НЕ предложено — смотреть в первую очередь на подпись
манифеста и на `issued`.

## Если ключ подписи манифестов сменился

Старые сборки его не знают и перестанут обновляться: у них вшит прежний открытый
ключ. Единственный путь — раздать новую сборку руками, как первую установку. Поэтому
`release keygen --force` и требует явного флага.

## Чего этот порядок НЕ защищает

Взлома рабочей станции. Оба ключа лежат на ней, и потеря машины означает потерю
обоих. Разносить их по разным машинам имеет смысл только если машины действительно
разные; пока это не так, и это записано честно в ADR 0014.
