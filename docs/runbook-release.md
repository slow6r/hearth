# Runbook: выпуск сборки и публикация обновления

Две подписи, и они разные. **Ключ APK** доказывает Android, что обновление от того же
автора, что установленное приложение. **Ключ манифеста** доказывает клиенту, что
список версий выпустили мы, а не захваченный узел. Оба лежат на рабочей станции, ни
один не копируется на узел.

Пропуск второй подписи не сломает установку — он сломает обновление у всех: сборка со
вшитым открытым ключом отказывается брать неподписанный манифест. Это осознанно: иначе
защиту выключал бы тот, от кого она защищает.

## 1. Подготовить дерево

```bash
cd android
scripts/bake-node.sh relay.myhearth.ru 7444   # адрес узла, CA, открытый ключ подписи
scripts/sync-overlay.sh                        # правки overlay → дерево форка
```

Закоммитить изменения **в форке** и перевыпустить патчи:

```bash
git -C simplex-chat add -A . && git -C simplex-chat commit
scripts/export-fork-patches.sh
```

Без этого сборка не пойдёт: `build-release.sh` отказывается собирать выпуск из
изменённого дерева. Так и задумано — именно этой проверки не хватило при выпуске
7.0.1-h15, когда APK ушёл людям, а исходники в git не попали, и аудит справедливо
спросил «из чего это собрано».

## 2. Собрать и подписать APK

```bash
scripts/build-release.sh
apksigner sign --ks ../keys/admin/hearth-release.jks --ks-key-alias hearth \
  --ks-pass file:<пароль> --key-pass file:<пароль> \
  --out hearth-<версия>.apk <собранный APK>
```

`apksigner` читает оба пароля из ОДНОГО файла последовательно, поэтому в файле должны
быть две строки с одним и тем же паролем. Иначе он падает с «end of file reached» —
это не ошибка ключа.

## 3. Проверить

```bash
scripts/verify-apk.sh hearth-<версия>.apk
```

Проверка падает от ошибки инструмента, а не проходит на пустом выводе. Она обязана
пройти целиком; «почти всё OK» означает, что сборку раздавать нельзя.

Сами проверки тоже проверяются: `scripts/tests/run.sh` гоняет их по фикстурам,
включая заведомо плохие (бэкап включён, сборка с отладкой, чужая подпись, секрет в
ресурсе).

## 4. Собрать и подписать манифест

```bash
sha256sum hearth-<версия>.apk
```

`manifest.json` — ровно эти поля:

```json
{
  "v": 1,
  "versionName": "7.0.1-h16",
  "versionCode": 387,
  "sha256": "<из sha256sum>",
  "file": "hearth-7.0.1-h16.apk",
  "issued": "<время выпуска, RFC 3339>",
  "notes": "<что изменилось, одной фразой для человека>"
}
```

`issued` обязано **расти**: клиент помнит самую свежую отметку и откажется от
манифеста старее. Это защита от заморозки — захваченный узел не может подсунуть своё,
но мог бы показывать старое.

Поля `expires` в исходном файле писать не нужно: его проставляет подпись — см. ниже.

```bash
hearthctl --config keys/admin/hearthd.toml release sign manifest.json \
  --key keys/admin/release-sign.key --valid-for 30d
hearthctl --config keys/admin/hearthd.toml release verify manifest.json --pubkey keys/admin/release-sign.pub
```

`sign` **перезаписывает** `manifest.json`, дописывая в него `expires`, и подписывает
уже новый файл. Поэтому порядок именно такой: сначала подпись, потом выкладка, и
никакой правки манифеста между ними — подписывается содержимое байт в байт, и любая
последующая правка (хоть пробел) делает подпись неверной. Проверять подпись у себя
обязательно.

`verify` печатает и срок: `свежесть: Ok — манифест действует ещё 30 дн.`.

### Срок годности: что это и почему его назначаете вы

Клиент больше не верит манифесту бесконечно. Есть `expires` — верит ему и возрастом не
судит. Нет `expires` — работает запас в **180 дней** от `issued`, а с седьмого дня
человеку показывается «узел молчит».

Здесь раньше стояло «30 дней», и это было просто неверно: в коде и на узле запас
равен 180 (`HearthUpdateTrust.MAX_MANIFEST_AGE_DAYS`, `hearthd` — `MAX_MANIFEST_AGE_DAYS`).
Запас этот работает только на манифестах ПРЕЖНЕГО образца — тех, что подписаны до
появления `expires`; у всего, что подписано этой командой, срок стоит всегда, и возраст
такой манифест не судит вовсе. Полгода — потому что переподписать статический
`manifest.json` может только эта машина, и месяц означал бы «выпускайте релиз хотя бы
раз в месяц, иначе семья останется без канала обновлений». Раньше этого срока человек
всё равно узнаёт о молчании узла — на седьмой день, — так что заметность держится не на
запасе, а на предупреждении.

Назначаете срок вы, а не узел, и причина простая: **ключ подписи лежит здесь, а на узле
его нет**. Узел физически не может переподписать манифест — ни сам, ни по вашей команде,
ни под принуждением того, кто его захватил. Именно поэтому бессрочный манифест был
дырой: захваченный узел мог годами показывать одно и то же и держать семью на версии с
известной уязвимостью.

- `--valid-for 30d` (умолчание, если флага нет) или `--valid-for 6w`;
- либо `--expires 2026-10-18` — годен весь этот день, отказ наступает со следующего;
- срок в прошлом и срок дальше года команда не примет: первое — манифест, который никто
  не поставит ни разу, второе — бессрочность, написанная другими словами.

Ставьте столько, через сколько **реально** дойдут руки до этой машины. Месяц — разумное
умолчание; полгода перед отъездом честнее, чем месяц и «потом продлю».

### Ваша обязанность: переподписать до истечения

Срок — это обещание, которое даёте вы. Что произойдёт, если его не сдержать:

| Когда | Узел | Семья |
|---|---|---|
| за 7 дней до | `updates=Degraded` в `hearthctl status`, **warning-алерт** | ничего не замечает |
| после срока | `updates=Down`, **critical-алерт**, строка в журнале на каждую выдачу | «срок годности манифеста обновления истёк» вместо предложения обновиться |

Переписка, звонки и файлы продолжают работать в любом случае: истёк срок только у
раздачи обновлений.

Узел при этом **не перестаёт отдавать** просроченный манифест — он не имеет права
отбирать у семьи уже выложенное обновление, а починить ситуацию всё равно может только
эта машина. Он делает единственное, что может: говорит об этом громко и заранее.

Лечение — повторить шаг 4 с тем же APK:

```bash
hearthctl --config keys/admin/hearthd.toml release sign manifest.json \
  --key keys/admin/release-sign.key --valid-for 30d
```

и выложить `manifest.json` и `manifest.json.sig` заново (шаг 5). Новая сборка для этого
не нужна: `versionCode` не меняется, меняется только срок.

Если добраться до этой машины прямо сейчас нельзя, а красный статус на узле мешает
видеть остальное, на **самом узле** под root можно убрать раздачу целиком:

```bash
rm /srv/hearth/updates/manifest.json /srv/hearth/updates/manifest.json.sig
```

Узел вернётся в `updates=Ok` с пометкой «обновление не публиковалось». Это не починка —
обновлений у семьи всё равно не будет, — но это честное состояние вместо просроченного,
и оно не требует ни ключа, ни работающего hearthd.

## 5. Выложить

На узел, в `updates_dir` (по умолчанию `/srv/hearth/updates`), владелец
`hearth:hearth`, права `0640`:

```
hearth-<версия>.apk
manifest.json
manifest.json.sig
```

Предыдущий APK убрать: манифест указывает ровно на один файл.

`versionCode` обязан строго расти — по нему клиент решает, новее ли сборка, и по нему
же отказывается откатываться.

## 6. Раскатка

Сначала одно устройство, сутки (ТЗ §10.6 п.3). Потом остальные.

Проверить на устройстве: обновление предложено, установилось, приложение запускается,
сообщения ходят. Если обновление НЕ предложено — смотреть в первую очередь на подпись
манифеста и на `issued`.

## Если ключ подписи манифестов сменился

Старые сборки его не знают и перестанут обновляться: у них вшит прежний открытый
ключ. Единственный путь — раздать новую сборку руками, как первую установку. Поэтому
`release keygen --force` и требует явного флага.

## Чего этот порядок НЕ защищает

Взлома рабочей станции. Оба ключа лежат на ней, и потеря машины означает потерю
обоих. Разносить их по разным машинам имеет смысл только если машины действительно
разные; пока это не так, и это записано честно в ADR 0014.
