# Runbook: роутер UDM для узла fels

Всё, что нужно сделать **на роутере**, чтобы узел стал доступен из интернета. Это
последний этап развёртывания: до него машина снаружи не видна, и это защита, а не
недоделка. Выполнять только когда узел уже поднят и `hearthctl health` зелёный.

Узел: `192.168.1.72` · публичный адрес: `185.145.126.254` · роутер: `192.168.1.1`

---

## 1. Проверить статичность публичного адреса — ДО выбора `node.host`

Провайдер называет услугу статической, письменного подтверждения нет, оператор в
разговоре назвал адрес динамическим. Это надо проверить фактом, потому что `node.host`
попадает в адрес каждого клиента и сменить его потом нельзя без того, чтобы все члены
семьи заново добавили все контакты ([runbook-rotate-address.md](runbook-rotate-address.md)).

```bash
# по ssh на роутер
ip -4 addr show pppoe-wan | grep inet        # записать адрес
kill -HUP "$(pgrep -x pppd)"                 # переустановить сессию, ~10 с простоя
sleep 20
ip -4 addr show pppoe-wan | grep inet        # адрес тот же?
```

Адрес тот же → статика подтверждена практикой (не договором, но хоть чем-то).
Адрес другой → **голый IP в `node.host` ставить нельзя**, только домен.

Десять секунд простоя всего дома. Делать не в час пик.

## 2. DNS-запись, если `node.host` — домен

Домен `you-can-do.ru` уже в Cloudflare, поддомен добавляется бесплатно.

dash.cloudflare.com → зона `you-can-do.ru` → **DNS → Records → Add record**:

| Поле | Значение |
|---|---|
| Type | `A` |
| Name | `relay` |
| IPv4 address | `185.145.126.254` |
| Proxy status | **DNS only** (серое облако) |
| TTL | Auto |

**Серое облако обязательно.** Оранжевое означает, что Cloudflare терминирует TLS у
себя. Отпечаток CA релея зашит в адрес клиента, и клиент, увидев чужой сертификат,
откажется подключаться. Это правильное поведение клиента, а не сбой — но выглядит как
«мессенджер не работает».

Cloudflare проксирует только HTTP(S); 5223, 5443 и 3478 через оранжевое облако не
проходят вообще.

Проверка:

```bash
dig +short relay.you-can-do.ru        # должен вернуть 185.145.126.254, не 104.21.x.x
```

## 3. Проброс портов

UniFi Network → **Settings → Routing & Firewall → Port Forwarding**. Все правила ведут
на `192.168.1.72`, порт снаружи = порт внутри.

| Имя | Порт | Протокол | Зачем | Обязателен |
|---|---|---|---|---|
| hearth-smp | 5223 | TCP | SMP — основной порт релея | да |
| hearth-smp-443 | 443 | TCP | SMP — обход ограниченных сетей и гостиничного Wi-Fi | да |
| hearth-xftp | 5443 | TCP | XFTP — передача файлов | да |
| hearth-turn-udp | 3478 | UDP | STUN/TURN — согласование звонка | да |
| hearth-turn-tcp | 3478 | TCP | то же для сетей, где UDP зарезан | да |
| hearth-turn-media | 49160–49200 | UDP | **медиапоток звонков** | да |

Последнее правило — то, которое забывают. Без него звонок соединяется, сигнализация
выглядит здоровой, и в трубке тишина.

### Что НЕ пробрасывать — ни при каких условиях

| Порт | Что это | Что будет |
|---|---|---|
| 22 | ssh | ssh узла в интернете |
| 7443 | admin API hearthd | управление узлом в интернете |
| 9090 / 9093 / 9100 | Prometheus, Alertmanager, node_exporter | метрики и внутренности хоста наружу |
| 47984–48010 | Sunshine | **удалённый доступ к рабочему столу в интернете** |

Доступ ко всему этому остаётся по LAN и через ZeroTier. На самом узле они уже закрыты
фаерволом, проброс был бы вторым замком, который открыли изнутри.

### Проверить, что 443 не забрал себе роутер

UniFi OS слушает 443 для своей панели. Доступ к ней с WAN по умолчанию закрыт, и
правило проброса должно иметь приоритет, но это надо подтвердить фактом — снаружи:

```bash
curl -sk https://185.145.126.254/ | head -3
```

Ответ релея (мусор, не HTML) — правильно. HTML-страница UniFi — правило не сработало,
разбираться до того, как раздавать адреса клиентам.

## 4. Правило 904

Костыль, который уводил трафик туннеля Cloudflare в VPN в обход провайдерского NAT.
С белым адресом причина исчезла.

Порядок: **сначала наблюдение, потом удаление.** Убрать правило → сутки смотреть на
`systemctl status cloudflared` и на доступность you-can-do.ru снаружи. Держится —
удалять насовсем. Не держится — вернуть и записать почему.

Не убирать одновременно с пробросом портов: если что-то сломается, будет непонятно,
что именно.

## 5. Проверка снаружи

Запускать **не из дома**. Подойдёт любой VPS или телефон по мобильному интернету.

```bash
TARGET=<node.host> ./tests/acceptance/a04-port-scan.sh
```

Или руками:

```bash
for p in 5223 443 5443 3478; do nc -vz -w5 <node.host> $p; done   # должны открыться
for p in 22 7443 47984; do nc -vz -w5 <node.host> $p; done        # должны молчать
```

Настоящая проверка звонков — только звонок между двумя телефонами в **разных**
мобильных сетях (тест A8). Диапазон 49160–49200 сканом не проверяется осмысленно:
порт открывается на время конкретной TURN-аллокации.

## 6. Если адрес всё-таки сменился

Три места, и все три обязательны:

1. A-запись в Cloudflare;
2. `external-ip=<новый>/192.168.1.72` в `/etc/hearth/templates/turnserver.conf.tmpl`,
   затем `hearthctl rotate turn-secret` (перерендерит `/etc/turnserver.conf`);
3. правила проброса, если роутер привязывает их к WAN-адресу.

Пункт 2 забывают, и это стоит дорого: сигнализация работает, звонки молчат, потому что
coturn продолжает объявлять старый ICE-кандидат.
