# Runbook: роутер UDM для узла fels

Всё, что нужно сделать **на роутере**, чтобы узел стал доступен из интернета. Это
последний этап развёртывания: до него машина снаружи не видна, и это защита, а не
недоделка. Выполнять только когда узел уже поднят и `hearthctl health` зелёный.

Узел: `192.168.1.72` · публичный адрес: `185.145.126.254` · роутер: `192.168.1.1`

---

## 1. Проверить статичность публичного адреса — ДО выбора `node.host`

Провайдер называет услугу статической, письменного подтверждения нет, оператор в
разговоре назвал адрес динамическим. Это надо проверить фактом, потому что `node.host`
попадает в адрес каждого клиента и сменить его потом нельзя без того, чтобы все члены
семьи заново добавили все контакты ([runbook-rotate-address.md](runbook-rotate-address.md)).

```bash
# по ssh на роутер
ip -4 addr show pppoe-wan | grep inet        # записать адрес
kill -HUP "$(pgrep -x pppd)"                 # переустановить сессию, ~10 с простоя
sleep 20
ip -4 addr show pppoe-wan | grep inet        # адрес тот же?
```

Адрес тот же → статика подтверждена практикой (не договором, но хоть чем-то).
Адрес другой → **голый IP в `node.host` ставить нельзя**, только домен.

Десять секунд простоя всего дома. Делать не в час пик.

**Что выяснилось на этой линии (2026-09-09).** История PPPoE из логов роутера: с
30 июля по 8 сентября восемь сессий подряд получали один и тот же CGNAT-адрес
`10.24.193.254`, а 9 сентября в 15:16 сессия переустановилась и адрес стал белым —
`185.145.126.254`. То есть привязку к линии провайдер делает, но **белый адрес
сменился на последнем же переподключении**, и истории у него нет.

Проверку разрывом сессии не проводили: провайдер, судя по всему, перенастраивал линию
за час до этого, и переподключение могло попасть в незаконченную перенастройку. Именно
эта история и есть причина, по которой `node.host` — домен, а не голый IP.

## 2. DNS-запись

`node.host` = **`relay.myhearth.ru`**. Домен отдельный, не поддомен `you-can-do.ru`, и
это не вкусовщина: `you-can-do.ru` резолвится в адреса Cloudflare, а реальный адрес
сервера спрятан за туннелем. Поддомен с записью `DNS only` опубликовал бы origin игры
под тем же доменом — перебор поддоменов это первое, что делают при атаке на сайт за
Cloudflare.

DNS обслуживает Timeweb (`ns1..ns4.timeweb.ru/org`). Запись:

| Поле | Значение |
|---|---|
| Тип | `A` |
| Хост | `relay.myhearth.ru` |
| Значение | `185.145.126.254` |
| TTL | 600 |

Если зона когда-нибудь переедет в Cloudflare — **только серое облако (DNS only)**.
Оранжевое означает, что Cloudflare терминирует TLS у себя; отпечаток CA релея зашит в
адрес клиента, и клиент, увидев чужой сертификат, откажется подключаться. Это
правильное поведение клиента, а не сбой, но выглядит как «мессенджер не работает».
Через оранжевое облако 5223, 5443 и 3478 не проходят вообще.

Проверка:

```bash
dig +short relay.myhearth.ru        # 185.145.126.254
```

Зона расходится не мгновенно: после регистрации домена резолверы час-другой отдают
SERVFAIL. Пробросу это не мешает — правила ведут на IP.

## 3. Проброс портов

UniFi Network → **Settings → Routing & Firewall → Port Forwarding**. Все правила ведут
на `192.168.1.72`, порт снаружи = порт внутри.

| Имя | Порт | Протокол | Зачем | Обязателен |
|---|---|---|---|---|
| hearth-smp | 5223 | TCP | SMP — основной порт релея | да |
| hearth-smp-443 | 443 | TCP | SMP — обход ограниченных сетей и гостиничного Wi-Fi | да |
| hearth-xftp | 5443 | TCP | XFTP — передача файлов | да |
| hearth-turn-udp | 3478 | UDP | STUN/TURN — согласование звонка | да |
| hearth-turn-tcp | 3478 | TCP | то же для сетей, где UDP зарезан | да |
| hearth-turn-media | 49160–49200 | UDP | **медиапоток звонков** | да |

Последнее правило — то, которое забывают. Без него звонок соединяется, сигнализация
выглядит здоровой, и в трубке тишина.

### Как это сделать не руками (UniFi OS 5.1.19)

Два пути мимо панели, и работает только второй — проверено на этой машине.

**Через iptables напрямую — не делайте.** Правила заработают сразу и исчезнут при
первой же переконфигурации: смена любой настройки, перезагрузка, обновление прошивки.
Приложение Network пересобирает набор правил целиком. Для мессенджера это худший вид
отказа — работает неделю, потом молча перестаёт.

**Через базу контроллера напрямую — не работает.** Документы в `ace.portforward`
ложатся, но приложение за своей базой не следит: конфиг шлюза оно пересобирает только
когда изменение пришло через его собственный API. Перезапуск `unifi.service` не
помогает — проверено, DNAT так и остаётся нулевым, в логе приложения ни слова.

**Через API приложения — так и надо.** Контроллер валидирует, применяет и показывает
правила в панели.

```bash
# 1. вход в UniFi OS (аккаунт ui.com -> потребуется код 2FA с почты)
curl -sk -X POST https://192.168.1.1/api/auth/login      -H 'Content-Type: application/json'      -d '{"username":"...","password":"...","token":"<код 2FA>"}'      -c /run/unifi.cookie -D /run/unifi.headers

# 2. csrf-токен из заголовков ответа
CSRF=$(grep -i 'csrf-token' /run/unifi.headers | tail -1 | sed 's/.*: *//' | tr -d '
')

# 3. правило
curl -sk -X POST https://192.168.1.1/proxy/network/api/s/default/rest/portforward      -H 'Content-Type: application/json' -H "x-csrf-token: $CSRF"      -b /run/unifi.cookie      -d '{"name":"hearth-smp","enabled":true,"pfwd_interface":"wan","src":"any",
          "destination_ip":"any","dst_port":"5223","fwd":"192.168.1.72",
          "fwd_port":"5223","proto":"tcp","log":false}'
```

Ответ `{"meta":{"rc":"ok"}}`. Проверка, что дошло до дата-плоскости:
`iptables -t nat -S | grep DNAT` — правила появляются в `UBIOS_PREROUTING_USER_HOOK`
с привязкой к WAN-адресу (`--match-set UBIOS_KEY_ADDRv4_ppp0 dst`).

Пароль в командной строке виден в `/proc/<pid>/cmdline`. Либо собирайте тело запроса
из файла с правами 0600 и стирайте его после (`shred -u`), либо заведите временного
админа и удалите его следом.

### Что НЕ пробрасывать — ни при каких условиях

| Порт | Что это | Что будет |
|---|---|---|
| 22 | ssh | ssh узла в интернете |
| 7443 | admin API hearthd | управление узлом в интернете |
| 9090 / 9093 / 9100 | Prometheus, Alertmanager, node_exporter | метрики и внутренности хоста наружу |
| 47984–48010 | Sunshine | **удалённый доступ к рабочему столу в интернете** |

Доступ ко всему этому остаётся по LAN и через ZeroTier. На самом узле они уже закрыты
фаерволом, проброс был бы вторым замком, который открыли изнутри.

### Проверить, что 443 не забрал себе роутер

UniFi OS слушает 443 для своей панели. Доступ к ней с WAN по умолчанию закрыт, и
правило проброса должно иметь приоритет, но это надо подтвердить фактом — снаружи:

```bash
curl -sk https://185.145.126.254/ | head -3
```

Ответ релея (мусор, не HTML) — правильно. HTML-страница UniFi — правило не сработало,
разбираться до того, как раздавать адреса клиентам.

## 4. Правило 904

Костыль, который уводил трафик туннеля Cloudflare в VPN в обход провайдерского NAT.
С белым адресом причина исчезла.

Порядок: **сначала наблюдение, потом удаление.** Убрать правило → сутки смотреть на
`systemctl status cloudflared` и на доступность you-can-do.ru снаружи. Держится —
удалять насовсем. Не держится — вернуть и записать почему.

Не убирать одновременно с пробросом портов: если что-то сломается, будет непонятно,
что именно.

## 5. Проверка снаружи

Запускать **не из дома**. Подойдёт любой VPS или телефон по мобильному интернету.

```bash
TARGET=<node.host> ./tests/acceptance/a04-port-scan.sh
```

Или руками:

```bash
for p in 5223 443 5443 3478; do nc -vz -w5 <node.host> $p; done   # должны открыться
for p in 22 7443 47984; do nc -vz -w5 <node.host> $p; done        # должны молчать
```

Настоящая проверка звонков — только звонок между двумя телефонами в **разных**
мобильных сетях (тест A8). Диапазон 49160–49200 сканом не проверяется осмысленно:
порт открывается на время конкретной TURN-аллокации.

## 6. Если адрес всё-таки сменился

Три места, и все три обязательны:

1. A-запись `relay.myhearth.ru` у регистратора;
2. `external-ip=<новый>/192.168.1.72` в `/etc/hearth/templates/turnserver.conf.tmpl`,
   затем `hearthctl rotate turn-secret` (перерендерит `/etc/hearth/turn/turnserver.conf`);
3. правила проброса — на UDM они привязаны к WAN-адресу через
   `--match-set UBIOS_KEY_ADDRv4_ppp0`, то есть переезжают за адресом сами.

Пункт 2 забывают, и это стоит дорого: сигнализация работает, звонки молчат, потому что
coturn продолжает объявлять старый ICE-кандидат.
