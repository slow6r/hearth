### 3. Что не закрыто

1. **Карантин и миграция.** Сохранились ошибки отказа записи режима, повторной остановки и слишком позднего hold миграции. Установленные unit-файлы не проверяют mode перед самостоятельным стартом. Текущий закрытый runtime mode не прочитан, поэтому не утверждается, что работающий узел прямо сейчас нарушает карантин.
2. **Регистрация и отзыв доступа.** При `allow_device_enroll=true` конкурентный отзыв родителя оставляет ребёнка с рабочим доступом. Ошибки persistence оставляют изменения памяти/квоты, повторный claim может создавать дубликаты, issue_admin не соблюдает общий lock. Эти ветви повторно воспроизведены на новом source. Default enrolment=false; фактический live-параметр пока неизвестен.
3. **Строгая клиентская политика.** Не устранены обязательная свежесть manifest, несовместимость guard с API26–27, отсутствие byte cap APK, отдельные проблемы own-host/expiry/startup/restore. Дополнительный AES-слой звонков не обязателен, relay/ICE изменяемы. Базовое DTLS-SRTP сохраняется; способность обычного TURN расшифровать звонок не установлена.
4. **Новые ограниченные риски Android.** Для стикеров SHA-проверка необязательна, возможны duplicate grid keys, нет бюджета decoded image dimensions. Huawei fallback broadcast может раскрыть подходящему стороннему receiver счётчик непрочитанных сообщений. Это условные проблемы целостности/доступности/метаданных; Android crash, RCE или утечка содержимого не доказаны.
5. **Backup и наблюдаемость.** Source допускает успешный архив при отсутствующем required source и не распознаёт отсутствие отдельных counters. Актуальные config/state/nft и восстановление внешней копии остаются непроверенными из-за недоступных данных. Зелёного статуса daemon недостаточно для закрытия этих замечаний.
6. **Серверная среда.** GDM настроен на автовход fels; Secure Boot выключен; на видимом блочном стеке нет LUKS/шифрованного swap. Coturn остаётся 4.6.1-2. Текущая графическая сессия и полный sudoers не проверены; свежий закрытый TURN config не прочитан.
7. **iOS и все смартфоны.** Native Android APK — ARM64/minSdk26; поддержка всех Android не обеспечена. NTF и dump timer live disabled/inactive. Подписанный рабочий IPA и реальные iPhone↔Android/push тесты не представлены. Новый Android bundle/patch-series больше не передаёт прежний интегрированный iOS snapshot, хотя overlay, инструкции и старый commit в истории сохранены.

### 4. Оставшаяся граница доказательств

Файлы релиза проверены независимо. Однако авторизованный GET production с проверкой реально возвращённых байтов, установка поверх приложения и длительные сообщения/звонки/фон на телефонах ещё не испытаны. APK signer и совпавшие библиотеки не доказывают воспроизводимость всего приложения из Git commit; независимая полная сборка не выполнялась.

Связь установленного hearthd с исходным commit также не доказана. `/srv/hearth/src` читается, но Git не распознал его как репозиторий; четыре найденных release-бинаря не совпали с установленными файлами. Это **не доказательство компрометации или другой логики**: возможны разные параметры/артефакты сборки. Нужен паспорт именно установленного бинарника; `/proc/PID/exe` сейчас закрыт.

В source-каталоге обнаружено 14 091 читаемый файл без доступной auditor записи. Файлов с указанными потенциально секретными именами не найдено; содержимое массово не читалось. Вывод «секретов нет вообще» из одного поиска расширений не следует.

Для завершения закрытых проверок достаточно целевой обезличенной выгрузки, не передачи private keys и не общего sudo. Группы журналов не откроют config/state; автоматически добавлять обе adm/systemd-journal не требуется.

Каталог `D:/ОЧАГ` существует в среде текущего сеанса аудита. Это не утверждение о путях на машине администратора. На сервере использованы явно предоставленные Linux-пути. Production, ACL, группы, приложение на телефонах и публикация h22 аудитором не изменялись.

## Часть 2. Фактические APK h21 и h22

Полученные по SSH файлы проверены локально. Оба проходят криптографическую проверку APK Signature Scheme v2/v3 ожидаемым сертификатом, содержат защиту обновлений, совпадающее официальное нативное ядро и ожидаемые публичные ресурсы. Это существенно уменьшает прежнюю неопределённость «есть только исходники». Однако сохранённые ограничения свежести обновлений, политики звонков и порядка применения настроек остаются в коде APK. Проверка не доказывает полную воспроизводимость сборки, работу на телефоне или невозможность доступа третьих лиц при любых обстоятельствах.

### Что подтверждено именно в DEX

1. **Встроенный ключ действительно подключён к проверке обновлений.** UI вызывает `HearthReleaseKey.pinned`, передаёт результат и `HearthReleaseKey::verify` конструктору checker; тот запрашивает signature sidecar и применяет `HearthUpdateTrust`. Реальный verifier использует `EC`/`SHA256withECDSA`, вызывает `initVerify`, `update(body)` и `verify(signature)`. Lookup идёт по имени `hearth_release_key`, связанному выше с фактическим публичным ключом.
2. **Guard APK включён в службу.** После download вызывается `HearthApkGuard.inspect`; только Allow ведёт к уведомлению установки. Guard читает package/version/`apkContentsSigners`, а rules сравнивают пакет, точную ожидаемую и установленную версии и текущие сертификаты. Это подтверждает исправление прежнего отсутствия проверки identity; фактическая установка поверх приложения не тестировалась.
3. **Ограничения update trust остались.** В DEX сохранился Allow при отсутствии pinned key; у конкретных APK ключ присутствует, читаемый и правильный, поэтому это не доказанный обход проверки этих двух сборок. Freshness сравнивает строку issued только с lastSeenIssued и допускает равную; обязательной проверки календарного возраста в `decide` нет. Сценарий замораживания требует воспроизведения настоящего ранее подписанного манифеста. Сохранился также прямой доступ к API-28 `PackageInfo.signingInfo` при заявленном minSdk26; это статическая проблема совместимости Android 8, без проведённого runtime crash test.
4. **Неограниченный download APK и Startup/bundle/TURN пути сохраняются.** Извлечены скомпилированные классы download, Startup, Bundle, Turn credentials и Android TURN adapter; они одинаковы у h21/h22 и согласуются с рассмотренным исходным поведением. Ранее описанные ограничения не закрыты сменой h21 на h22.
5. **Звонки и защита экрана.** `CallActivity.onCreate` устанавливает `FLAG_SECURE` (`0x2000`). В обработчике CallOffer цепочка через synthetic lambda до `processReceivedMsg$lambda$40` передаёт `sharedKey` в `WCallCommand.Offer`, не читая `askConfirmation`; `call.js` тот же, где AES зависит от наличия ключа. Сохранено ограничение обязательности прикладного AES/согласия на совместимость. Это не доказательство расшифровки TURN-сервером или внешнего MITM; штатное DTLS-SRTP не объявляется сломанным.
6. **Huawei badge fallback присутствует.** Скомпилирован прямой `Context.sendBroadcast(Intent)` без receiver permission, как в текущем исходнике. Возможное раскрытие ограничено unread count/фактом использования приложения при выполнении fallback и наличии стороннего receiver; содержимое сообщений и токены этим выводом не затрагиваются.

### Метод и предел результата

Использованы SDK build-tools 36.1.0 (`apksigner`, `aapt2`, `zipalign`), SDK apkanalyzer под Java 21, Python 3.14/cryptography 49. Проверены подпись каждого APK, manifest/resources/XML, SHA содержимого ZIP, ключи/CA только в публичной форме, выборочная дизассемблировка DEX, сравнение с текущими исходниками и нативным официальным эталоном. В DEX отсутствуют проверенные marker prefixes Google/Firebase/Play/Crashlytics/Sentry/AppsFlyer/Amplitude и пять известных публичных relay/STUN строк; это ограниченный поиск, не динамическое доказательство отсутствия любой телеметрии или внешнего трафика.

Полный `verify-apk.sh` как один pipeline не запускался; перечисленные проверки выполнены отдельными реальными инструментами, без подмены verifier. Старые Kotlin/gate fixture tests не выдаются за тесты этих установленных APK. Полная Gradle-сборка, воспроизводимость каждого DEX, установка/обновление телефона, backup restore, звонки между устройствами, трафик во время background и уведомления на Huawei не проверялись. Приватные ключи и пользовательское содержимое не читались; сервер/телефон не изменялись.
