# ADR 0005 — Свой минимальный HTTP вместо клиентского крейта

**Статус:** принято · **Дата:** 2026-09-06 · **Основание:** ТЗ §7.2, §7.4

## Контекст

`hearthd` должен уметь отправить алерт в Gotify на UDM Pro (`10.66.0.1`). Обычный
инструмент для этого — `reqwest` или `ureq`.

## Решение

Отправка алерта — примерно 30 строк: TCP-соединение через `EgressPolicy` +
руками собранный HTTP/1.1 POST (`src/alerts/notify.rs`). HTTP-клиентских крейтов в
дереве зависимостей нет; `reqwest`, `ureq`, `curl`, `native-tls` внесены в `deny.toml`
как запрещённые.

## Обоснование

Дело не в размере зависимости, а в **возможностях**, которые она приносит:

- клиент общего назначения умеет резолвить имена — а у узла нет резолвера (ТЗ §5.2) и
  не должно быть возможности его использовать;
- умеет ходить по редиректам — то есть по адресу, которого не было в конфиге;
- умеет TLS к произвольному хосту с системным trust store;
- имеет пулы, прокси, переменные окружения (`HTTP_PROXY`), которые меняют назначение
  запроса неочевидным образом.

Всё это — ровно те способности, которых у узла быть не должно. Наш вариант умеет
единственное: POST на один IP-литерал, проверенный политикой перед открытием сокета.
Токен передаётся заголовком `X-Gotify-Key`, а не в URL, чтобы не попасть в чужой лог.

## Последствия

- Нет ретраев и keep-alive — для алертов не нужно: журнал остаётся источником истины,
  а неудачная доставка логируется.
- Gotify обязан быть внутри `home_networks`; конфиг с внешним адресом не проходит
  валидацию (тест `rejects_external_alert_target`).
- Для admin API используется `hyper` — тот же, что и на серверной стороне. Это не
  «клиент общего назначения»: он говорит по одному адресу и доверяет одному CA.
