# ADR 0007 — Публичный релей вместо доступа только через WireGuard

**Статус:** принято · **Дата:** 2026-09-07 · **Заменяет:** ТЗ §5 (сетевой контур), §3.1 (строка про DPI), §10.3 п.2

## Решение

Релеи SMP/XFTP и TURN доступны из интернета, как любой другой сервер SimpleX.
WireGuard из схемы доступа убран. На LAN остаются только admin API `hearthd` и ssh.

## Контекст

ТЗ строило доступ через существующий семейный WireGuard. Владелец указал, что SimpleX
так не разворачивают: сервер рассчитан на публичную доступность, а содержимое и без
туннеля защищено E2E-шифрованием и отпечатком CA в адресе.

Это верно по существу. Разбор upstream (simplexmq v7.0.1) подтверждает: `install.sh`
ставит сервер с публично слушающими портами, дефолт `port = 5223,443` выбран именно
для пробивания ограниченных сетей, а `[TRANSPORT] host` вообще не биндит —
«only used to print server address on start».

Дополнительный аргумент, который решает дело: **звонки**. Когда оба собеседника за NAT
(два телефона в мобильных сетях — обычный случай), медиапоток идёт через TURN. TURN,
доступный только внутри VPN, не может быть точкой встречи для двух устройств, которые
в этот VPN не входят. Требование «голосовые и видеозвонки работают» и модель
«только через WG» несовместимы без always-on VPN на всех устройствах.

## Что мы теряем — прямо и без смягчений

**Метаданные.** SimpleX прячет их *на релее*: нет аккаунтов, нет идентификаторов
пользователей. Но наблюдатель на канале (провайдер каждого члена семьи) видит:
«устройство X держит TLS-соединение с адресом Y, столько-то часов, столько-то данных».
Домашний IP становится известной точкой мессенджера. Это то, что раньше закрывал WG,
и это не компенсируется ничем другим в текущей схеме.

**Поверхность атаки.** До релейных парсеров теперь дотягивается интернет, а не 20
устройств. ТЗ §3.2 принимало риск 0-day «снижаем только скоростью апгрейда» — это
обоснование ослабло, и §1.4 п.4 (security-релиз за ≤ 7 дней) из пожелания становится
обязательством.

**Второй замок.** Раньше на создание очереди было два: попасть в WG и знать пароль.
Остался один — `create_password` в `[AUTH]`. Он теперь несущий.

## Что сделано, чтобы это было приемлемо

| Мера | Где |
|---|---|
| Пароль на создание очередей и загрузку файлов — обязателен | `relays/*/`*.ini.example*, проверяется A3 |
| admin API и ssh — только LAN, wildcard-бинд API отвергается конфигом | `Config::validate`, тест `admin_api_may_not_be_exposed` |
| TURN не может быть использован для доступа в домашнюю сеть | `denied-peer-ip` на все приватные диапазоны в шаблоне coturn |
| TURN не превращается в чужой бесплатный релей | `use-auth-secret` + ротация + квоты |
| Узел по-прежнему не может «позвонить домой» | output policy drop; единственное исключение — медиатрафик coturn, ограниченный по `skuid` и диапазону портов |
| Порт 443 для пробивания ограниченных сетей | `smp.extra_ports`, `CAP_NET_BIND_SERVICE` в юните |

Детектор egress сохранён и остаётся осмысленным: клиенты подключаются *внутрь*, а
исходящих соединений у узла по-прежнему быть не должно. Ожидаемое значение
`egress_drop` — ноль.

## Что осталось нерешённым

- **Метаданные никак не закрыты.** Если это станет важно, вариант без возврата к
  всеобщему VPN — onion-адрес релея (SimpleX это умеет: `[PROXY] host_mode`,
  `socks_mode`). Тогда домашний IP не светится, а VPN на устройствах не нужен.
  Цена — задержки и зависимость от доступности Tor.
- **TURNS требует сертификата** на `node.host`, то есть домена и certbot. Без него
  звонки не пройдут из сетей, где открыт только 443/tcp. Порт 443 при этом уже занят
  под smp — развести придётся осознанно.
- **Регуляторный статус** публично доступного сервера отличается от домашнего сервиса
  в LAN. ТЗ §14 оценивало риск как низкий для «непубличного семейного контура»; эта
  оценка сделана для другой конфигурации.
