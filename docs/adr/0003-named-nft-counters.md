# ADR 0003 — Именованные счётчики nftables

**Статус:** принято · **Дата:** 2026-09-06 · **Уточнение к:** ТЗ §5.3

## Контекст

В наброске правил ТЗ §5.3 используются анонимные счётчики:

```
counter log prefix "hearth-egress-drop " drop
```

Анонимный счётчик привязан к правилу и **не появляется** в `nft list counters`. Прочитать
его можно только распарсив текст правил и сопоставив позиции — хрупко и неоднозначно.

## Решение

`deploy/nftables/hearth.nft` объявляет именованные счётчики (`egress_drop`, `input_drop`,
`forward_drop` и по счётчику на каждый разрешённый сервис) и ссылается на них из правил:

```
counter name egress_drop limit rate 10/second burst 20 packets \
    log prefix "hearth-egress-drop " level warn
drop
```

`hearthd` читает `nft -j list counters table inet hearth` и разбирает JSON.

## Обоснование

- Тот же эффект (счёт + лог + drop), но результат адресуем по имени и парсится как JSON,
  а не как текст правил.
- `limit rate` на строке лога защищает journald от затопления, **не влияя на счётчик**:
  `counter` выполняется до `limit`, поэтому число пакетов остаётся точным даже когда
  логирование подавлено. Это важно: цифра — основной сигнал, лог — уточнение.
- Разделение на два правила (счёт+лог, затем `drop`) необходимо, потому что при
  превышении `limit` правило перестаёт совпадать; вердикт вынесен отдельной строкой.

## Последствия

- Правила чуть длиннее.
- `hearthd` при пустом списке счётчиков сообщает «ruleset не загружен» — то есть
  отсутствие правил тоже становится наблюдаемым событием, а не тишиной.
