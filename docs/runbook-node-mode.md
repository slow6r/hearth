# Runbook — режим узла и что делать, если релеи не поднимаются

Про механизм целиком — [ADR 0013](adr/0013-node-mode.md). Здесь только действия.

У узла есть режим: `normal`, `quarantine`, `maintenance`, `migration`. Он лежит в
`<paths.state_dir>/node-mode.json` (по умолчанию `/var/lib/hearth/node-mode.json`),
переживает перезапуск демона и перезагрузку машины и снимается только человеком.

Пока режим не `normal`, узел не обслуживает семью ничем: smp, xftp, ntf и coturn не
поднимаются надзором, останавливаются при старте демона и не стартуют по
`systemctl start` — их юниты спрашивают гейт (`ExecCondition`) и помечаются
**пропущенными**. В `journalctl -u smp-server` это выглядит так:

```
Starting SimpleX SMP server...
hearth: старт запрещён — режим: карантин с 2026-09-17 21:04 UTC — хеш smp-server не совпал
hearth: файл режима: /var/lib/hearth/node-mode.json
hearth: снять режим на самом узле (root, без hearthd и без сертификата): hearthctl mode clear --local — см. docs/runbook-node-mode.md
smp-server.service: Skipped due to 'exec-condition'.
```

## 1. Узнать, в каком режиме узел

```bash
hearthctl mode show          # через admin API, если hearthd работает
hearthctl status             # режим печатается первой строкой
```

Без работающего hearthd — прямо на узле, ничего не поднимая:

```bash
sudo hearthctl mode gate ; echo $?      # 0 — релеям можно, 1 — запрет
sudo cat /var/lib/hearth/node-mode.json
```

`mode gate` берёт путь из `paths.state_dir` вашей конфигурации: если `state_dir` на
этом узле нестандартный, смотреть файл вручную нужно там же.

## 2. Снять режим

**Обычный путь** — через работающий демон, с админским сертификатом:

```bash
hearthctl mode clear
```

**Аварийный (локальный) путь** — на самом узле, с правами root, без hearthd, без сети
и без сертификата. Он существует именно для вечера, когда узел не поднялся.

Дальше всё зависит от того, ЖИВ ли hearthd. Команда сама спросит об этом systemd и
напечатает нужный случай, но знать оба полезно заранее.

**Случай А: hearthd работает** (`systemctl is-active hearthd` → `active`). Это самый
частый карантин — по целостности: демон жив и здоров, остановлены только релеи.

```bash
sudo hearthctl mode clear --local
# Всё. Надзор перечитывает файл режима на КАЖДОМ тике (check_interval_secs,
# по умолчанию 15 с), увидит норму и поднимет релеи сам.
systemctl is-active smp-server xftp-server coturn   # через ~15 с: active
```

Перезапускать демон не нужно. Если через минуту релеи не поднялись — значит дело не в
режиме; смотрите `hearthctl status` и `journalctl -u hearthd -n 50`, а демон можно
перезапустить: `sudo systemctl restart hearthd`.

**Случай Б: hearthd не работает** (не стартует, остановлен, в карантине по preflight).

```bash
# Если hearthd крутится в перезапусках — сначала остановите его, иначе он запишет
# запрет обратно раньше, чем вы успеете поднять релеи:
sudo systemctl stop hearthd
sudo hearthctl mode clear --local
sudo systemctl start smp-server xftp-server coturn hearthd
```

Команда пишет в файл режима `normal` и оставляет запись в журнале алертов узла
(`/var/lib/hearth/alerts.jsonl` и постоянная история) — карантин, снятый руками, не
должен выглядеть в разборе как исчезнувший сам собой. Файл и журналы создаются с
владельцем каталога состояния (`hearth:hearth`), а не root: иначе следующий старт
демона упёрся бы в собственный файл.

Сначала устраните причину. `hearthctl mode show` печатает её и находки; для карантина
по целостности это расхождение хешей — см. [A12](acceptance-tests.md#a12--sha256-бинарей-против-манифеста).

## 2a. hearthd не стартует вовсе

Два случая, которые выглядят одинаково — «релеев нет и демона нет», — и лечатся одним.

**Повреждён `node-mode.json`.** Демон больше не падает из-за этого: он поднимается,
считая узел запрещённым к обслуживанию, и пишет в журнал

```
файл режима /var/lib/hearth/node-mode.json не прочитан (...); до починки узел
считается запрещённым к обслуживанию
```

Гейт на том же файле отвечает запретом (битый файл не отличим от подчищенного).
Лечится одной командой — она терпит битый файл и перезаписывает его целиком:

```bash
sudo hearthctl mode clear --local
```

**Не прошёл preflight** (нет `/etc/hearth/pki/ca.pem` или `/etc/hearth/manifest.toml`).
Демон останавливается ОДИН раз, с кодом 78, и systemd его не перезапускает
(`RestartPreventExitStatus=78`). Раньше здесь была петля: каждые 5 секунд демон заново
записывал карантин и заново останавливал релеи, так что локальное снятие «не держалось»
дольше пяти секунд.

**Сломан `/etc/hearth/hearthd.toml`** — тот же код 78 и та же остановка один раз.
Нечитаемый файл, недописанная строка TOML, невыполнимый инвариант (чужой отпечаток в
пин-листе, адрес алертов вне домашней сети, порт admin API, занятый релеем) — всё это
состояние узла, которое правит человек; следующий запуск застанет ровно тот же файл.
Раньше это считалось «повторяемым» отказом: журнал заполнялся одной и той же строкой
разбора каждые пять секунд, и настоящую причину в этой ленте было не найти. Что делать
с релеями, которые при этом продолжают работать, — см. §3.

**Не читается журнал алертов или каталог состояния достался root.** Это НЕ повод не
стартовать, и демон больше не падает: он поднимается, пишет в journal и в алерты
жалобу и работает дальше (в худшем случае нумерация алертов начинается заново, уже
записанное остаётся в файле). Выход — §7.

```bash
journalctl -u hearthd -n 30 --no-pager     # причина названа словами
# почините названное (hearthd ca init / вернуть manifest.toml), затем:
sudo hearthctl mode clear --local
sudo systemctl start hearthd
```

## 2b. Узел только что установлен, а релеи не поднимаются сами

Симптом: в журнале раз в час `не запинено бинарей: N (...)`, `hearthctl status`
показывает режим **норма**, релеи работают, но упавший релей надзор обратно не
поднимает.

Это не карантин. В поставочном `manifest.toml` хеши — нулевые плейсхолдеры, и пока
они там, узел не может подтвердить, что именно на нём работает. Запинить всё, включая
`turnserver`, о котором легко забыть:

```bash
sudo hearthctl manifest pin --name smp-server  --version <tag>
sudo hearthctl manifest pin --name xftp-server --version <tag>
sudo hearthctl manifest pin --name turnserver  --version distro
grep -n 'sha256 = "0\{64\}"' /etc/hearth/manifest.toml   # ждём только ntf-server
```

Режим при этом снимать не нужно: его никто не ставил. Настоящее расхождение хешей —
другое событие, и оно по-прежнему даёт карантин.

## 3. Сломан `/etc/hearth/hearthd.toml`

Симптом: в журнале при КАЖДОМ решении гейта, в том числе разрешающем,

```
hearth: ВНИМАНИЕ: конфигурация узла недоступна — /etc/hearth/hearthd.toml не
прочитан (...); решение принято по пути по умолчанию /var/lib/hearth/node-mode.json
```

Релеи при этом **поднимаются**, если по пути по умолчанию нет запрета. Это осознанный
выбор: переименованный или недописанный конфиг — ошибка администратора, а не атака, и
платить за неё связью семьи не за что. Тот, кто может переписать `hearthd.toml`, тем
же движением снимет и сам файл режима, так что отказ ради безопасности здесь почти
ничего не покупал, а стоил всего.

Записанный на диск запрет при этом продолжает действовать: гейт читает
`/var/lib/hearth/node-mode.json` и запрещает старт, если там не `normal`.

```bash
# 1. Посмотреть, что именно сломано:
sudo hearthctl mode gate ; echo $?
sudo head -40 /etc/hearth/hearthd.toml

# 2. Если нужно снять запрет — команда пишет тот же файл по умолчанию:
sudo hearthctl mode clear --local

# 3. Починить конфигурацию — образец лежит в поставке:
#    hearthd/deploy/hearthd.toml
sudo hearthctl --config /etc/hearth/hearthd.toml health   # после старта демона
```

**Остаточный риск, названный честно.** Если `paths.state_dir` на этом узле
нестандартный И конфигурация сломана, гейт судит по пустому пути по умолчанию, то есть
запрет с такого узла слетит до починки конфигурации. Строка предупреждения в journal —
единственное, что об этом скажет. Файл режима в таком случае указывают явно:

```bash
sudo hearthctl mode clear --local --file <ваш state_dir>/node-mode.json
```

## 4. Крайний случай: снять сам гейт

### Как распознать пропавший hearthctl

Юнит пропущен, но в `journalctl -u smp-server` НЕТ ни одной строки `hearth:` — только

```
smp-server.service: Skipped due to 'exec-condition'.
```

Это не запрет режима, а неудачный запуск самого гейта: systemd отвечает на такой
`ExecCondition` кодом 203, а 203 попадает в диапазон «условие не выполнено». Причины
обычные: `/usr/local/bin/hearthctl` усечён (кончилось место при `install`), собран под
другую архитектуру, `/usr` на не смонтированном разделе. Проверка:

```bash
ls -l /usr/local/bin/hearthctl
/usr/local/bin/hearthctl mode gate --file /nonexistent/x.json ; echo $?   # ждём 0
systemctl show smp-server.service -p ExecCondition --value
```

Лечение — переустановить hearthctl (`hearthd/deploy/install.sh` проверяет его ДО любых
изменений на узле) либо, если связь нужна сию минуту, снять гейт.

### Снять гейт

Если релеи нужны немедленно, а разобраться не выходит, гейт снимается как обычный
drop-in:

```bash
sudo rm -f /etc/systemd/system/{smp-server,xftp-server,ntf-server,coturn}.service.d/hearth-mode.conf
sudo systemctl daemon-reload
sudo systemctl start smp-server xftp-server coturn
```

Это **выключает защиту**: узел снова будет поднимать релеи после перезагрузки, даже в
карантине. Так можно жить один вечер, не дольше. Вернуть — повторным запуском
`hearthd/deploy/install.sh` (он же проверит, что hearthctl на месте и работает).

## 5. Перенос узла

После `hearthctl migrate import` узел остаётся в режиме `migration` намеренно: два
живых релея с одним CA и одним адресом — это потерянные сообщения. Снимать режим
нужно **локально** и только после того, как старый узел выключен, а проброс портов
переключён:

```bash
sudo hearthctl mode clear --local
sudo systemctl enable --now smp-server xftp-server coturn hearthd
```

Сетевое `hearthctl mode clear` на этом шаге не работает: hearthd ещё не запущен —
импорт сам отказывается идти при живом демоне.

## 6. Что мешает демону стартовать, а что — нет

Список короткий, и разница в нём важнее самого списка: узел семьи обязан подниматься и
объяснять беду, а не исчезать.

**Останавливают демон насовсем (код 78, перезапуска не будет):**

* не прошёл preflight — нет `/etc/hearth/pki/ca.pem` или `/etc/hearth/manifest.toml`;
* сломан `/etc/hearth/hearthd.toml` — не читается, не разбирается или не проходит
  `Config::validate` (чужой отпечаток в пин-листе, адрес алертов вне домашней сети,
  порт admin API, занятый релеем).

Оба случая — состояние узла, а не сбой процесса, и оба разобраны в §2a.

**Не мешают стартовать — демон поднимается, говорит и работает дальше:**

* `backup.required_paths` содержит путь, которого нет в `backup.paths`. Требование
  невыполнимо по построению, и раньше `Config::validate` на нём отказывал — то есть
  опечатка в списке путей оставляла дом без надзора, целостности, бэкапа, алертов и
  admin API при работающих релеях, а значит незаметно. Теперь это **предупреждение**:
  строка уходит в journal и в алерты при каждом старте, а ночной прогон валит вердикт
  бэкапа в `Down`, пока списки не сойдутся. Молча это не проходит, но и связь семьи
  этого не стоит;
* повреждён `node-mode.json` — узел считается запрещённым к обслуживанию (§2a);
* не читается `alerts.jsonl` или каталог состояния достался root — §7.

Посмотреть всё это одной командой, не запуская демон:

```bash
sudo hearthd --config /etc/hearth/hearthd.toml check   # ошибки и предупреждения словами
```

## 7. Права и владельцы: `deploy/fix-permissions.sh`

Штатный выход из владельческих тупиков — один, и он скриптом:

```bash
sudo hearthd/deploy/fix-permissions.sh --dry-run   # показать, что будет сделано
sudo hearthd/deploy/fix-permissions.sh
sudo systemctl restart hearthd && hearthctl health
```

Скрипт идемпотентен и чинит, среди прочего, ровно те случаи, из-за которых узел
выглядит сломанным без видимой причины:

* **каталог состояния достался root** (`/var/lib/hearth`, `/var/opt/hearth`). Самый
  обидный случай: наследование владельца берёт его у каталога, поэтому root-овый
  каталог молча раздаёт `root:root` всему, что в нём создаётся. Локальное снятие
  режима отчитывается успехом, а демон при следующем старте не читает собственный
  файл режима. Скрипт возвращает обоим каталогам `hearth:hearth` рекурсивно;
* **журналы алертов достались root** (`alerts.jsonl`, `egress-incidents.jsonl`) — тем
  же `chown -R`. Демон при этом стартует и без починки, но пишет жалобу и начинает
  нумерацию заново;
* `node-mode.json`, `devices.json`, секреты, TLS-материал admin API, каталоги релеев и
  push-сервера, конфиг coturn.

Обе команды — и жалоба демона в journal, и предупреждение `hearthctl` на экране —
называют этот скрипт: если вы видите слово `fix-permissions.sh`, запускать нужно
именно его. Проверка после — `sudo tests/acceptance/a14-permissions.sh`.
