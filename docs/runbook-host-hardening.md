# Runbook: среда узла `fels` — что закрывается без переустановки

Этот файл отвечает на один вопрос: **что на `fels` можно сделать прямо сейчас, что —
в окно обслуживания, а что честно остаётся принятым риском до переустановки.**

Он появился после аудита 2026-09-18 (п. 3.6 «Серверная среда»), который снял с живого
узла состояние и нашёл расхождение между документами и фактом:
[ADR 0009](adr/0009-no-full-disk-encryption.md) засчитывал «разделение пользователей»
как выполненную компенсацию отсутствия LUKS, а на узле его нет.

Связанное: [ADR 0008](adr/0008-multi-purpose-host.md) (почему узел многоцелевой),
[ADR 0009](adr/0009-no-full-disk-encryption.md) (почему нет LUKS),
[runbook-install-beelink.md](runbook-install-beelink.md) (эталонная схема с двумя
пользователями, которая на `fels` не применялась).

## 0. Снятое состояние (18.09.2026, только чтением)

| Что | Факт |
|---|---|
| Display manager | `gdm3`, сессия Wayland, seat0 активна |
| `/etc/gdm3/daemon.conf` | `AutomaticLoginEnable=true`, `AutomaticLogin=fels` |
| sudoers | `fels ALL=(ALL:ALL) ALL` **и** `fels ALL=(ALL) NOPASSWD: ALL`; NOPASSWD продублирован в `/etc/sudoers.d/99-fels` |
| Secure Boot | disabled, платформа в **Setup Mode** (PK не записан) |
| Диск | `sda1` vfat `/boot/efi`, `sda2` ext4 `/`, `sda3` ext4 `/var`, `sda4` **swap**, `sda5` ext4 `/srv`. Ни одного `crypto_LUKS` |
| swap | отдельный раздел `sda4`, **не зашифрован** |
| coturn | установлен `4.6.1-2`, кандидат в репозиториях Debian 13 — тот же `4.6.1-2` |
| ntf-server, ntf-db-dump.timer | inactive/disabled |

Из первых трёх строк складывается одно предложение, которое стоит произнести целиком:
**машина круглосуточно стоит в зале с открытой сессией пользователя, которому `sudo`
не задаёт вопросов.** Десять секунд у клавиатуры — это `/etc/opt/simplex` (ключ CA
релея), `/etc/hearth/secrets` (пароли создания очередей) и `/root/.cloudflared`
(origin you-can-do.ru). Ни LUKS, ни Secure Boot к этому сценарию отношения не имеют:
они про выключенную машину, а эта — включённая.

### Чего в этом списке нет: sudo для демона

Соблазнительная правка — «заменить `NOPASSWD: ALL` на список команд, нужных `hearthd`».
Её сделать нельзя, потому что списка не существует: **`hearthd` не вызывает `sudo`
никогда.**

- юнит работает от `User=hearth` с `AmbientCapabilities=CAP_NET_ADMIN`
  (`hearthd/deploy/systemd/hearthd.service`) — этого хватает на `nft -j list counters`,
  единственный вызов `nft` в демоне (`hearthd/src/sys/nft.rs`);
- мутирующие `systemctl start/stop/restart` разрешены правилом polkit
  `hearthd/deploy/polkit/49-hearthd.rules` — закрытым списком из четырёх юнитов
  (`smp-server`, `xftp-server`, `ntf-server`, `coturn`) и пяти глаголов;
- `systemctl show` — чтение, прав не требует.

Значит `sudo` на этом узле нужен **только человеку**, и именно поэтому сузить его до
списка команд не выйдет (см. §1.2): почти всё, что человек делает с узлом, —
`install.sh`, `fix-permissions.sh`, `nft -f`, `apt` — root-эквивалентно по построению.
Реализуемое сужение здесь ровно одно: **вернуть пароль**.

## 1. Группа А: делается сегодня, без простоя

### 1.1. Проверить, что вы вообще видите текущее состояние

```bash
sudo tests/acceptance/a18-host-env.sh
```

Скрипт только смотрит и печатает вердикт. С него начинается и им же заканчивается
любая правка из этого файла.

### 1.2. Убрать `NOPASSWD` у `fels`

Это единственный шаг, который меняет картину «физический доступ = полный доступ»
**сегодня и без окна обслуживания**. После него человек у телевизора получает
десктоп-сессию `fels`, но не root, а ключи релея лежат `0600 root:root` — то есть
компенсация, которую [ADR 0009](adr/0009-no-full-disk-encryption.md) обещал, начинает
работать на самом деле.

Порядок, который не оставляет запертой двери — тот же, что в
[runbook-auditor-access.md](runbook-auditor-access.md): **не закрывать рабочую дверь,
пока новая не проверена.**

```bash
# 1. У fels должен быть пароль. Без него sudo с паролем = потеря доступа.
sudo passwd -S fels          # ожидается P (password set), не L и не NP
sudo passwd fels             # если вывод был L или NP

# 2. Держите открытым root-шелл в ОТДЕЛЬНОМ окне и не закрывайте его до конца шага.
sudo -i

# 3. В этом root-шелле: убрать дубль NOPASSWD.
cp -a /etc/sudoers.d/99-fels /root/99-fels.pre-nopasswd-$(date +%F)
rm /etc/sudoers.d/99-fels
visudo -c                    # обязателен: битый sudoers = sudo не работает ни у кого

# 4. Если строка NOPASSWD есть и в самом /etc/sudoers — убрать её ТОЛЬКО через visudo
#    (он проверяет синтаксис перед записью):
visudo
#    оставить: fels ALL=(ALL:ALL) ALL
#    удалить:  fels ALL=(ALL) NOPASSWD: ALL

# 5. Сбросить закешированный билет и проверить из ДРУГОГО окна:
sudo -K
ssh fels@192.168.1.72 "sudo -n true; echo \"-n вернул \$?, ожидается не 0\""
ssh -t fels@192.168.1.72 "sudo true"   # должен спросить пароль и пустить
```

Root-шелл из шага 2 закрывается последним — после того, как шаг 5 отработал.

**Что это ломает.** Любую неинтерактивную автоматику от имени `fels`, которая ходила
через `sudo` молча. В репозитории такой нет: таймеры и юниты работают от `root`,
`hearth` и `simplex*`, `hearthd` sudo не вызывает (см. §0). Но если у владельца есть
свои cron/скрипты на узле — они начнут спрашивать пароль и молча падать. Проверьте
перед шагом 3:

```bash
crontab -l -u fels; sudo ls -l /etc/cron.d/; systemctl list-timers --all
```

**Цена.** Каждое `sudo` теперь спрашивает пароль — включая те, что вы делаете по SSH
из другой комнаты. Это и есть вся суть шага: пароль знает владелец, а не тот, кто
проходил мимо телевизора.

### 1.3. Блокировка экрана: почему здесь развилка, а не рецепт

Очевидный ход — включить локскрин:

```bash
# от имени пользователя сессии
gsettings set org.gnome.desktop.screensaver lock-enabled true
gsettings set org.gnome.desktop.screensaver lock-delay 0
```

**Что это ломает.** Sunshine на этой машине стримит именно графическую сессию.
Залоченная сессия GNOME под Wayland не отдаёт ни картинку, ни ввод: Moonlight с
телевизора увидит экран блокировки, а разблокировать его удалённо нечем. То есть
«пришёл, включил занятие с телефона» перестаёт работать, пока кто-нибудь не подойдёт
к клавиатуре.

Поэтому:

- **если Sunshine используется без человека у машины** — локскрин по бездействию не
  включаем, оставляем `lock-enabled false`, а барьером служит §1.2. Это записанный
  риск, а не забытая настройка;
- **если Sunshine не нужен** — включаем обе строки выше; тогда §1.2 и локскрин
  складываются;
- **компромисс без потерь**: `lock-enabled true`, но блокировать **вручную** (`Super+L`
  или `loginctl lock-session`), когда зал не используется. Автоматики нет — значит и
  Moonlight ничего не ломает.

**Чего не трогать ни в одном из вариантов:** `idle-delay` (телевизор обязан гаснуть) и
маску `sleep.target suspend.target hibernate.target hybrid-sleep.target`
(`hearthd/deploy/install.sh`, блок 8). Сон узла = семья без сообщений.

### 1.4. Зафиксировать версию coturn и начать её мерить

Факт на 18.09.2026: установлено `4.6.1-2`, кандидат в Debian 13 — **тот же** `4.6.1-2`.
Обновления нет; см. §3.4, почему это не повод собирать из исходников.

```bash
dpkg-query -W -f='${Package} ${Version} ${Status}\n' coturn
apt-cache policy coturn
sudo apt-get -s upgrade coturn        # симуляция: ничего не ставит
```

Раз в неделю — строкой в «Журнал» [runbook-updates.md](runbook-updates.md): дата,
установленная версия, кандидат, вердикт. Пункт аудита должен закрываться фактом, а не
молчанием. Автоматически это же сверяет `a18-host-env.sh` (переменная `COTURN_MIN`).

## 2. Группа Б: нужно окно обслуживания

Окно — это время, когда допустимо, что телевизор в зале на минуту потеряет картинку
или сеть, а узел один раз перезагрузится. Мессенджер при перезагрузке сообщений не
теряет (A7), но у `you-can-do.ru` на этой же машине origin, туннель и платежи —
предупредите.

### 2.1. Перенести автовход на пользователя без sudo

Цель: у телевизора логинится `hall`, у которого нет sudo; `fels` остаётся только
административным входом по SSH. Тогда §1.3 перестаёт быть развилкой — залоченный
экран вообще не нужен, потому что за незалоченным ничего нет.

Порядок нельзя переставлять: **первым идёт фаервол**, иначе зал молча теряет интернет,
а незнакомое имя в `meta skuid` вообще не даст загрузить ruleset
(`hearthd/deploy/nftables/hearth.nft`, примечание про `skuid`).

```bash
# 1. Пользователь. Имя `hall`, а не `gym`: `gym` уже занято смыслом в
#    runbook-install-beelink.md как имя из эталонной схемы.
sudo adduser hall
sudo -n -l -U hall            # ожидается отказ: hall не должен уметь sudo
groups hall                   # в списке не должно быть sudo

# 2. Фаервол — ДО переноса сессии. В hearthd/deploy/nftables/hearth.nft правило
#    app_egress получает ещё одно имя:
#      meta skuid { "root", "_apt", "fels", "hall", "youcando", "zerotier-one", \
#                   "systemd-timesync" } counter name app_egress accept
sudo cp -a /etc/hearth/nftables/hearth.nft /root/hearth.nft.pre-hall-$(date +%F)
sudo nft -c -f /etc/hearth/nftables/hearth.nft     # ТОЛЬКО проверка, не загрузка
# Загрузка под автооткатом: если новое правило заперло связь, через 5 минут вернётся
# прежний файл, и идти в зал не придётся.
sudo systemd-run --on-active=5min --unit=nft-rollback \
     nft -f /root/hearth.nft.pre-hall-$(date +%F)
sudo nft -f /etc/hearth/nftables/hearth.nft
# Убедиться, что связь жива и счётчики на месте, затем снять откат:
hearthctl egress
sudo systemctl stop nft-rollback.timer 2>/dev/null || true
sudo systemctl reset-failed nft-rollback 2>/dev/null || true

# 3. Sunshine: перенести автозапуск/сессию с fels на hall, перепарить Moonlight.
#    Правила фаервола для Sunshine привязаны к адресам, не к uid — их менять не надо.

# 4. Автовход:
sudo cp -a /etc/gdm3/daemon.conf /root/daemon.conf.pre-hall-$(date +%F)
sudoedit /etc/gdm3/daemon.conf            # AutomaticLogin=fels -> AutomaticLogin=hall
grep -vE "^[[:space:]]*(#|$)" /etc/gdm3/daemon.conf
sudo systemctl restart gdm3               # <-- это и есть простой: сессия зала перезапустится

# 5. Проверить вживую, ДО следующего шага: Moonlight подключается, Zoom и браузер
#    выходят в сеть, app_egress растёт, egress_drop = 0.
sudo tests/acceptance/a02-egress-zero.sh
sudo tests/acceptance/a18-host-env.sh

# 6. Только теперь — убрать `fels` из app_egress (он больше не инициирует трафик):
#    правка hearth.nft тем же порядком, что шаг 2, с `nft -c -f` и автооткатом.
```

`hall` в `AllowUsers` sshd **не добавлять**: `/etc/ssh/sshd_config.d/99-server.conf`
остаётся `AllowUsers fels auditor`.

**Что это ломает, если ошибиться.** Несуществующее имя в `meta skuid` = ruleset не
грузится целиком, вместе с ним пропадает входной фильтр и связь семьи. Убрать `fels`
из `app_egress` раньше переноса сессии = у телевизора молча пропадает интернет, а
трафик занятий начинает капать в `egress_drop` и превращает детектор утечки релея в
шумящий. Перезапуск `gdm3` закрывает всё, что было открыто в сессии зала.

### 2.2. Зашифровать swap случайным ключом

Единственная часть шифрования диска, которая реализуема **без переустановки и без
компромисса «ключ рядом с замком»**. Работает она потому, что swap не обязан пережить
перезагрузку: гибернация на узле замаскирована (`install.sh`, блок 8), значит ключ
можно брать из `/dev/urandom` и нигде не хранить.

Что сейчас в этом swap может лежать: куски памяти `hearthd` — пароли создания очередей
и `static-auth-secret` coturn проходят через неё при выпуске bundle и ротации
(`hearthd/src/configgen/turn.rs`).

```bash
# 0. Снять состояние ДО правки и сохранить вывод:
swapon --show; cat /proc/swaps; lsblk -o NAME,FSTYPE,TYPE,SIZE,MOUNTPOINT
blkid /dev/sda4
systemctl is-enabled hibernate.target   # обязано быть masked
sudo cp -a /etc/fstab /root/fstab.pre-swapcrypt-$(date +%F)
sudo cp -a /etc/crypttab /root/crypttab.pre-swapcrypt-$(date +%F) 2>/dev/null || true

# 1. /etc/crypttab — по PARTUUID, а не по UUID: mkswap переписывает UUID при каждой
#    загрузке, и запись по UUID перестанет находить раздел ровно со второго раза.
#      swap_crypt PARTUUID=<partuuid sda4> /dev/urandom swap,cipher=aes-xts-plain64,size=256

# 2. /etc/fstab — старую строку про sda4 заменить на:
#      /dev/mapper/swap_crypt none swap sw,nofail 0 0
#    `nofail` здесь обязателен: без него ошибка в этих двух строках превращается в
#    машину, которая ждёт устройство и не поднимается, а в зале никого нет.

# 3. Применить и проверить БЕЗ перезагрузки:
sudo swapoff -a
sudo systemctl daemon-reload
sudo systemctl start systemd-cryptsetup@swap_crypt.service
sudo swapon -a
swapon --show                  # ожидается /dev/mapper/swap_crypt
sudo dmsetup ls --target crypt # swap_crypt должен быть в списке

# 4. Контрольная перезагрузка — и только она считается проверкой:
sudo reboot
# после: hearthctl health; swapon --show; sudo tests/acceptance/a18-host-env.sh
```

Альтернатива, если возиться не хочется: `sudo swapoff -a` + удалить строку swap из
fstab (проверив по `free -h`, что памяти хватает) или `apt install zram-tools`. Оба
варианта закрывают тот же риск: на диске не остаётся незашифрованной копии памяти.

**Что это ломает.** Ошибка в `crypttab`/`fstab` = машина не загружается сама после
отключения света, а это ровно тот сценарий, ради которого BIOS настроен на
`Restore on AC power loss = Power On`. Отсюда `nofail`, бэкапы обоих файлов в `/root/`
и обязательная контрольная перезагрузка при человеке рядом. И: гибернацию
**не размаскировывать никогда** — со случайным ключом образ гибернации не прочитается,
и это порча данных, а не неудобство.

### 2.3. Обновление coturn, когда оно появится

Сегодня обновлять нечего (§1.4). Когда кандидат станет новее:

```bash
apt-get changelog coturn | head -40                 # сначала читаем
sudo cp -a /etc/hearth/turn/turnserver.conf /root/turnserver.conf.pre-upd-$(date +%F)
sudo cp -a /etc/turnserver.conf /root/etc-turnserver.conf.pre-upd-$(date +%F)
sudo apt-get install --only-upgrade coturn          # юнит перезапустит сам
```

После: `systemctl status coturn` (active); на вопрос «оставить вашу версию конфига?» —
**оставить свою**; STUN Binding Request снаружи отвечает; и обязательно — звонок между
двумя телефонами. Ротация TURN-секрета при обновлении **не нужна**: секрет к версии
пакета отношения не имеет.

**Что это ломает.** `apt upgrade` на этой машине трогает не только мессенджер: рядом
боевой стек `you-can-do.ru` (nginx, Next.js, MongoDB/Redis в docker, cloudflared).
Обновляйте `--only-upgrade` точечно, а не всё сразу. Потеря `/etc/turnserver.conf` при
обновлении = звонки соединяются и молчат — самый трудный в отладке симптом проекта.

## 3. Группа В: переустановка, физический доступ, принятый риск

Здесь ничего не «делается». Здесь написано, чем мы платим и почему.

### 3.1. LUKS на весь диск — только переустановка

Обоснование целиком в [ADR 0009](adr/0009-no-full-disk-encryption.md). Коротко:
привести `fels` к требованию можно лишь переустановкой ОС и повторным развёртыванием
всего стека игры. Разумный момент — следующая замена железа.

### 3.2. Шифрование только каталогов данных — отвергнуто, и это не лень

`/etc/opt/simplex`, `/etc/hearth`, `/var/opt/simplex`, `/srv/hearth` обязаны
примонтироваться при автозагрузке без человека (BIOS: `Power On` после пропадания
питания). Значит ключ от такого раздела лежит рядом на незашифрованном диске — это
шифрование, ключ от которого приклеен к замку. Единственное исключение — swap (§2.2):
ему ключ хранить не нужно вовсе.

### 3.3. Secure Boot — включать не будем, и это не улучшение

Сейчас: disabled, платформа в **Setup Mode** (PK не записан — то есть любой, кто
добрался до BIOS, запишет туда свои ключи).

Почему включение не считается исправлением: при незашифрованном корне тот, кто добрался
до диска, правит `initramfs` и юниты напрямую — подпись загрузчика этому не мешает.
Secure Boot имеет смысл **только вместе с FDE**, и прежде всего в варианте «LUKS с
разблокировкой по TPM» (ради него в BIOS включён Intel PTT): там ключ распечатывается
по PCR, а при выключенном Secure Boot PCR не измеряют ничего содержательного.

Цена попытки: BIOS правится только руками, у машины, стоящей в зале; после включения
узел может не загрузиться (сторонние модули — ZeroTier, Docker), и это простой связи
семьи и сайта игры на неопределённое время ради свойства, которое без FDE ничего не
даёт. **Принято как риск до переустановки.**

### 3.4. Coturn новее, чем в Debian 13 — осознанный отказ

Три варианта и почему выбран третий:

| Вариант | Что даёт | Чем платим |
|---|---|---|
| Backports | пакет собирает Debian, обновления приходят штатно | `coturn` в `trixie-backports` может не быть вовсе — проверять `apt-cache policy -t trixie-backports coturn` до того, как на это рассчитывать |
| Сборка из исходников | самая свежая версия | выпадаем из потока security-обновлений Debian: следить за CVE, пересобирать и перезапускать сервис на публичном 3478 придётся вручную. Модуль `integrity` пинует только свои бинари (`/etc/hearth/manifest.toml`), дистрибутивные пакеты он не измеряет — свой `turnserver` окажется единственным исполняемым файлом узла, происхождение которого никто не проверяет |
| **Остаёмся на `4.6.1-2` из Debian** | security-фиксы приходят бэкпортом от Debian в той же версии пакета | версия выглядит старой и будет выглядеть так дальше; за трекером безопасности Debian надо смотреть глазами (§1.4) |

Отказ обоснован ещё и тем, что конфигурационная часть TURN закрыта полно:
аутентификация по короткоживущим кредам, полный `denied-peer-ip` (все приватные,
loopback, link-local, reserved), квоты, `no-cli`, работа от `turnserver:turnserver`
(`hearthd/deploy/coturn/turnserver.conf.tmpl`). Пересборка ради номера версии меняет
известный риск на неизвестный.

### 3.5. Что остаётся правдой при любом исходе

Человек, получивший **физический** доступ к включённой машине с правами root или к
BIOS, получает контур целиком. Закрывается это не настройками, а дверью в зал — строка
«Физический доступ к залу | вне контура проекта» в
[ADR 0009](adr/0009-no-full-disk-encryption.md) остаётся честной.
